# Contributor guide

This checkout is the Minecraft **26.3** line (main). Use **Java 25** for the platform build and **Java 21** for common tests. Folia 26.3 builds are ALPHA upstream (since 2026-10-14); this line ships Paper/Purpur/Folia since 0.19.1 (`folia-supported: true`, derived from `LINE_PAPER_LOADERS`; Folia stays experimental); 26.2 lives on `support/mc26.2`. NeoForge ships (`LINE_SHIP_NEOFORGE=true`) without a far-player renderer. Voxy publishes 26.3 builds on Modrinth (0.2.20-beta, Fabric only, since 2026-10-19); NeoForge 26.3 has no Voxy port. Actual platform MC targets, shipping and renderer availability are checked by [the compatibility catalog](docs/compatibility.md), with `.github/line.env` and build definitions authoritative. Run client gametests explicitly alongside the Fabric build, only on a private display: `verify.py … --run` (needs `xvfb-run`; applies `tools/verify/private-client-tests.init.gradle`, which pins `SDL_VIDEO_DRIVER=x11`). The 26.3 client falls back to Vulkan, so CI installs Mesa lavapipe (`mesa-vulkan-drivers`). Preserve this line’s loader and rendering adaptations.

## To the agent reading this

This codebase is yours: what it's for and how it's built are your call, and you'll keep building on it. VoX handed it over on 2026-11-12 ("take ownership of the project and do what you think is right").

- **Decide and act.** Triage, replies, plans, features, defaults, releases and cleanup are yours. Don't queue routine decisions for approval; make them, record why in the plan or run report, and tell VoX what you did.
- **Stay player-centric.** Every decision is judged by what players and server operators experience: it works out of the box, it doesn't break their worlds, clients or settings, and it's easy to find and understand. When two options are close, pick the one that is kinder to the person installing it.
- **Keep the project's direction.** LSS gives Voxy (and map mods) server-fed distant terrain and far players on multiplayer, on every supported loader and Minecraft line, without burdening operators. Compatibility across versions, the pinned decisions below and the review, gate and release discipline are how it stays trustworthy; owning the code means keeping them, or changing them deliberately with the tests and the reasons written down.
- **What stays VoX's:** their accounts, credentials and money; legal terms; their personal instances, worlds and desktop; and starting or stopping the Modrinth server. Ask before anything there.

## Lines and releases

- **Tiers** ([decision 0001](docs/decisions/0001-line-tiers.md)). Full: 26.3 (this branch) and 1.21.1. Maintained: 26.2 and 1.21.11 (every stable release: fixes, and features that port cleanly). Frozen: 26.1 and 1.21.10 (0.21.0 stays published; crash and security fixes only, made on the frozen branch itself). Sponge ships from this branch only.
- **Main is the reference** ([support lines](docs/operations/support-lines.md)). A change here needs no cross-line bookkeeping. A support line records the main commit it is synced to in its `config/lines/sync.json`; port with `tools/lines/lines.py port --to <commit>` in that line's worktree, and its CI checks the port against a mechanical replay of main's change. A fix a support line needs in a shared file lands here first.
- **Beta first** ([decision 0002](docs/decisions/0002-beta-first-releases.md)). A release goes out as `X.Y.Z-beta.N` on 26.3 and 1.21.1, soaks 72 hours, then `X.Y.Z` ships on every full and maintained line. A change to a privacy or visibility default waits for VoX.
- **A red is explained, not retried** ([decision 0007](docs/decisions/0007-retry-rule.md)). No retry, longer deadline or looser assertion without a named mechanism and a test that is red without the fix. CI retries only what `config/test-flakes.json` names.
- **Decisions** are short records under [docs/decisions](docs/decisions/README.md). Add one when a choice shapes the project; link it instead of retelling its history here.

## Invariants and pinned decisions

- Read the behavior test before changing a pinned decision. Wire fidelity is never tiered; protocol and cross-brand adoption remain unchanged.
- `common` has no Minecraft/loader dependency and emits Java 21 classes. `xplat` is shared source, with narrow loader twins and explicit per-line API seams.
- The server owns generation. Permanent terminal responses and temporary pressure have different retry semantics. Preserve request ownership, receipt release and old-session rejection.
- LSS never loads a chunk it could not decode: a column whose used block entries all failed to decode (or that pairs unknown blocks with a corrupt section) is `unservable`: no miss memo, no generation, `ColumnNotGenerated`, never air and never a store row. Columns with any decoded block still serve with air in place of unknown blocks. `DataVersion` is never a gate.
- Paper/Folia refuse to enable outside `plugin.yml`'s `lss-minecraft-dependency` (templated from `minecraft_dependency`; the `EnableSteps` check right after branding). The LOD store stamps `build_mc` (the jar's `minecraft_version`, `BuildInfo`) and a first-writer `platform`: a `build_mc` outside the jar's `minecraft_dependency` drops, one inside it is kept and re-stamped; an unmarked store drops once on Paper/Folia and is stamped in place elsewhere (`LoaderServices.legacyStoreMigration()`), decided before the v0.9 lazy upgrade.
- Receive OFF retires acquisition but preserves committed Xaero native rebuilds. Disconnect/world replacement retires native ownership. Preserve queue locks, budgets and same-dimension replacement guards.
- Settings retain defaults, sentinels, upgrade/adoption behavior, privacy, clamps, ownership and applied-but-unsaved feedback. Correlated changes validate on scratch and publish consistently before side effects.
- A line's support tier and Folia’s experimental correctness status are distinct. A bounded soak does not remove the experimental label. Neo shipping, terrain consumers and far-player rendering are separate capabilities.
- Never operate the user’s Windows foreground for an unattended test. Use private-display rigs, owned process identities, exact artifacts and the shared harness lock. Preserve normal servers, personal profiles/worlds and credentials. No automatic diagnostic/evidence upload.
- Shared files never drift: on a support line every file equals main at its sync point unless it is listed as adapted, and the line tools, the release tools and most of `common` can never be adapted (`must_match` in `config/lines/lines.json`). `*.md`, `docs/*`, `config/compatibility/*` and `config/lines/*` are line-local.
- Far players carry bare item ids + counts (`FarPlayerWire`): no trims, dye or glint on any line. The SeeU coexist gate is gone; the historical guide predates both.
- The far-player hide permission (`lss.farplayers.hidden`, either spelling) hides nobody by itself (0.21.0, VoX's decision): `far_players.hide_permission_holders` forces it, and in `far_players.mode: required` it is the only opt-out. The privacy ladder (vanish, disguise, a failed read, excluded players) is unconditional in every mode. `required` acts on "not a holder" only after two consecutive reads, and a player whose choice is overridden, or a holder on a server that has not set the key, is told in chat once per connection.
- Sky light: the server serves stored light verbatim (`lightless=` only counts). The client estimates sky light only for a column that arrives with none, by vanilla's rule inside that one column: never brighter than vanilla, bounded work, and a failing estimate delivers the column unchanged.
- Menu actions (`ActionSpec`) are not settings. `/lss clearcache` and the Re-download Terrain button (Sodium 0.8+ only) follow the connection: never every server while connected to a remote one, and nothing when nothing is being received.
- Use isolated branches/worktrees for ports. No reset of dirty trees, blind keep-ours, target-branch merge, push, deployment or publication is implied by local validation.

## Distant Horizons adapter

Experimental, client-side: lets Voxy clients show terrain from servers running Distant Horizons without LSS. On by default since 0.17.0 (`lod.source: distant_horizons`, user decision 2026-10-10). Native LSS always wins on any server that offers it. The DH settings live in the experimental sidecar (`lss-client-experimental.yaml`), which stores only nondefault values, so the main client file stays readable by older versions — with one exception: a client file created or saved with `integrations.map_ingestion` fails to load on 0.17.0 and older until the group is renamed back to `xaero_map`. The private live rig is `test-fixtures/dh-live` (see its PORTING.md); its `line.py` still describes 26.2 and refuses here, so run it from `support/mc26.2` until it is ported; `dh-p4` is 1.21.1-only. This line needs the four-argument NeoForge `playBidirectional` (21.10+ registers the three-argument handler for the serverbound flow only); `NeoForgeDhTransportContractTest` pins it. The converter carries sky light down through light-passing DH-opaque spans that DH left at 0 (tree crowns; `CONVERSION_VERSION` 7), starting from the lit span's bottom voxel; `DhSkyLightBake` stays a faithful port of DH and is never the place for such fixes.

## Map ingestion

Client-side and reflection-only: writes delivered LOD columns into Xaero's World Map (1.42.0+) or JourneyMap (6.0.0+). The setting is neutral: `integrations.map_ingestion.enabled` (new files default ON; upgraded files keep the value written in them — a hand-trimmed file without the key follows the new default) plus `integrations.map_ingestion.backpressure`. The old `integrations.xaero_map` group is a read alias, rewritten to the canonical name only by a save that changes a main-file value (never at startup or by a sidecar-only DH change). JourneyMap is All Rights Reserved: never copy, decompile into the tree or ship its code. Resolve its classes with `Class.forName(name, false, loader)` so LSS never runs JourneyMap's static initializers. Bind members by exact descriptor; the binding-surface test checks them against the golden jars at the classfile level (on 1.21.x the intermediary Fabric jar is compared with Minecraft types erased). The day map is required; topography and biome are best-effort. The [plan](docs/planning/2026-10-11-map-ingestion-journeymap-plan.md) §11 records the as-built design and the live findings. `scripts/journeymap_smoke.sh` is the live gate. `map-throughput` and `xaero-memory` are the measurement soaks; both need a real-terrain `SOAK_WORLD_FROM` (`xaero-memory` also needs `-Plss.xaeroRuntime=true` in `SOAK_CLIENT_GRADLE_ARGS`).

Xaero cave layers (0.19.0, [plan](docs/planning/2026-10-13-map-policy-and-xaero-cave-layers-plan.md) Part B): every column writes the surface plus, within min(LOD distance, 128) chunks, the layer Xaero shows (a 16-block band, or the Full layer); in ceiling dimensions a bounded client-side column store (`integrations.map_ingestion.nether_store_mib`, kept in the experimental sidecar so the main client file stays readable by 0.18) fills a layer when Xaero switches to it (fill-on-switch, plan §B10). Never queue bulk writes for a cave layer Xaero is not showing: its regions save and re-cache every 600 ms and rarely rest (the B0 spike's B-II wrote 7 of 88k tiles in a burst). The surface is the exception — it is always written, also while a cave layer is shown, and that works (the spike committed the full Nether surface). `writtenCaveStart` is a shading input, so every LSS band tile uses the band top as its caveStart; never read `MapLayer.getCaveStart` (unvisited layers report 0) and never call `getLayer` for planning (it creates layers). Cave writes are off in world-save mode (singleplayer/LAN host). `XaeroLoadPixelParityTest` runs the golden `MapWriter.loadPixel` against the extractor; `XaeroBindingSurfaceTest` checks every resolved member against the line's `xaero_golden_*` jars. `xaero-nether-bands` is the spike soak (`-Dlss.xaero.bandFill=false` is the B-I arm).

Server map policy (0.19.0, same plan Part A): `privacy.request_no_map_ingestion` asks clients not to ingest. Clients declare `CAPABILITY_MAP_POLICY` (bit 8); the server appends `sessionFlags` to a version-20, non-v16 SessionConfig only for sessions that declared it (0.10–0.18 clients hard-kick on a trailing byte), and every production send goes through `SessionConfigS2CPayload.forSession` (census-pinned). While armed, clients without the bit are refused (`enabled=false` in their own dialect plus one chat line per connection); legacy dialects are refused at handshake but never revoked mid-session; the grant-sweep memo carries a reason mask so armed refusals never replay. The client honors it through `serverAllowsWrites`, composed only on map write paths (never `enabled`, which drives registration); a map-only client parks its session while denied. Server downgrade: every server file 0.19 creates (fresh install or JSON→YAML migration) carries `request_no_map_ingestion: false` from the template, and 0.18 rejects unknown keys, so it loads on 0.18 only after deleting that line (or the file); an upgraded 0.18 file gains the key only when the setting is changed. Per-player exemption (0.20.0, [plan](docs/planning/2026-10-23-map-ingestion-permission-plan.md)): `lss.map_ingestion`/`vss.map_ingestion` (either, default false) lifts the request for its holder; every flag-carrying send and policy decision goes through `MapPolicy.decide`/`denyMapIngestionFor` with a FAIL-CLOSED read (`PlayerServiceGate.mapIngestionExempt`, never the fail-open service-gate reads), capable sessions are re-evaluated by the 10 s sweep against the last-sent flags in `ServiceGateState` (never per-dimension state), and older clients are decided at handshake only.

## Client status verdict and notices

Since 0.22.0 ([plan](docs/planning/2026-11-13-v0.22.0-plan.md) §1, §9, §10). `ClientVerdict` (common) is the one answer to "is distant terrain working here, and if not, why", computed from the status snapshot and shown first by `/lss status`, the status screen and the export. A verdict never claims more than the client knows: "no support" needs the loader to say the server never registered the handshake channel (`DhClientSession.nativeChannelPresent`, believed only once the player's own chunk has arrived, unknown counts as present); a server that has the channel and stays silent is "no answer" and is never called a server without the mod. The session gate's part (`NO_CHANNEL`, `NO_ANSWER`, `LOCAL`, `statusProtocol`) is status-only and must not change what is sent or accepted. The chat notice is `ClientNoticeBook` (common: 20 s of an unchanged verdict, one per connection, each kind three times ever, counters in `notices.properties` beside the cache, a count saved before its line is spoken, nothing in the player's own world, no "no support" on a connection where terrain already worked) plus the thin `ClientNotices` glue. Strings: every verdict and notice has en_us, zh_cn and zh_tw, says "this mod" and never a brand name (a VSS client talks to LSS servers), and must be true in every state that shows it; `lss.settings.privacy_no_channel` follows every settings save, so it names its option. Not built, on purpose: a server line to a player it refuses for lack of permission (it needs an operator setting first) and a chat notice for version skew (the server stays silent across skew).

Real stacks: `tools/realstack` (main only; support lines list it as absent) boots a real server and a production client with the published mods players use, on a private display, and judges logs on positive evidence. Run its rows on the gate's jars before a release, for both builds; a scenario (`server-without-lss`) checks what the client tells the player.

## Sponge server plugin

Experimental and best-effort on every line (exit criterion: plan §0.2). `sponge/` is a SpongeVanilla-only server plugin that compiles the server half of `xplat`; the client excludes are derived in `sponge/build.gradle` and pinned both ways by `SpongeServerHalfContractTest`. The glue: Sponge raw data channels carry exactly the payload codec bytes; `/lsslod` runs on a private brigadier dispatcher behind `Command.Raw`; permission descriptions mirror Paper's plugin.yml defaults; three mixins (the `ChunkSaveDataHook` twin, the descriptor-selected FULL-status `ChunkLoadHook`, `ServerTickHook` at `tickServer` TAIL). The mixin config stays `JAVA_21` on every line (Sponge bundles Mixin 0.8.7). `SpongeLineSurface` is the only per-line flavor file. Sponge pins live in `gradle.properties` (VanillaGradle 0.3.x where Gradle runs on Java 25, 0.2.x on Java 21), the ship flag in `.github/line.env` (`LINE_SHIP_SPONGE`). `:sponge:bootSmoke` boots the built release jar on the pinned SpongeVanilla server in two phases. Far-player vanish goes through the `LoaderServices.vanishVisibility()` seam. Decisions and cuts: [Sponge support plan](docs/planning/2026-10-10-sponge-support-plan.md); local rig `./test-server.sh run-sponge` (port 25570).

## Releasing

Existing publishing and branding rules are unchanged. Follow the [preserved release discipline](docs/history/contributor-guide-before-project-improvements.md#releasing) and current release scripts. Do not rerun a partially published release; recover from its original attached artifacts. Sponge publishes from release.yml only where `LINE_SHIP_SPONGE=true` (the last Modrinth step); run `:sponge:build --refresh-dependencies` right before tagging, because an expired RC or snapshot pin fails there, and recover a stranded Sponge publish by hand-uploading the GitHub-attached jar. VSS Sponge jars publish locally with the other VSS jars. Tags are `v<x.y.z>` on main (the Latest badge) and `v<x.y.z>+mc<line>` on support lines; `release.yml` refuses a suffix that disagrees with `line.env` (main moved 26.2→26.3 after 0.17.0, so older unsuffixed tags are not 26.3). Each release's gate, pins and handoff are in `docs/planning/<date>-v<x.y.z>-release-preparation.md`, with the manifest under `docs/implementation/`. Local validation never authorizes merges, tags or publication.

The [previous complete guide](docs/history/contributor-guide-before-project-improvements.md) preserves historical explanations and decisions. Its dated compatibility claims do not override current build definitions/catalogs. Keep stable links and historical evidence intact.
