## 1. The server thread's cost per chunk load and save (Fabric, NeoForge, Sponge)

### Evidence

`DirtyContentFilter` decides at every chunk save whether LOD-visible content changed, and seeds
its baseline at every chunk load. Both run on the server thread. Each call serializes the live
chunk (`SectionSerializer.serializeColumnInner`), translates the native bytes to the v20 layout
(`NbtSectionSerializer.toV20`), and hashes the result with a byte-at-a-time FNV-1a 64.

With one player flying at 40 blocks a second: about 140 calls a second, LSS code on the stack in
32 % of the server thread's busy samples, about 1.5 ms of each 50 ms tick. Inside that: the hash
28 %, the live serialization 24 % (plus 5 % for the non-zero light scan), the translation about
27 % (11 points of it parsing and validating block-state names, per call).

A second question was checked and closed: about half of the first saves after a load are marked
changed in that flight. A diagnostic that compares the load-time bytes with the first save's
showed real differences (blocks in 75 % of them, block light in most of the rest): vanilla's
post-processing of chunks that were pregenerated and never loaded. Not a seeding fault. Nothing
to fix.

### Design

1. **Hash the native bytes, not the v20 translation.** All three producers of a baseline go
   through `SectionSerializer` on a live chunk: the save hook, the load seed and the generation
   serve (`ChunkGenerationService`, the only caller of `seed`). The translation rewrites palette
   values and nothing else for indexed containers, and re-palettizes direct ones as a function
   of the voxel ids, so two native bodies are equal exactly when their translations are. The
   filter therefore hashes the native body: `SectionSerializer.nativeColumn(...)`, which is
   `serializeColumnInner` without its last step. The generation serve seeds from the live chunk
   it just serialized (`seedServed(level, chunk, ...)`), not from the served bytes.
2. **A fast hash.** A 64-bit hash that reads eight bytes at a time (`ContentHash64` in `common`,
   the XXH64 algorithm, checked against its published test vectors). The table lives in memory
   only, so nothing persistent changes. The all-air sentinel and the zero remap stay.
3. **Validated names are remembered.** `IdentityDictionary.indexOf` validates every identity
   again for every column. Identities come from the registry tables, so a process-wide set of
   strings that already passed (bounded, 65,536 entries; beyond it, validate without
   remembering) removes the parse. This also helps every cold serve and the backfill, which
   translate the same way. An invalid identity still throws every time: only passes are stored.
4. Not in this release: skipping the serialization when no block or light changed (it needs a
   change counter on the chunk: three more mixins), and moving the work off the server thread.
   Revisit with the numbers after 1 to 3.

`SaveObservation.sectionBytes` and `depositable` go: the store bridge has been delete-only since
the R2-M2 round and nothing reads them.

### What stays pinned

- A serve seeds the baseline; a probe serve does not; `newlyGenerated` chunks are not seeded at
  load; all-air hashes to the sentinel; LRU eviction; `forget`.
- The store's own content hash (CRC32C, persistent) is not touched.
- Fail-open: an error while hashing reads as changed.

### Tests

- `ContentHash64Test` (common): the published XXH64 vectors, every length from 0 to 64, one-bit
  avalanche, never returns 0 after the remap.
- `DirtyContentFilterTest`: the existing cases against the new seam; new: equal native bytes
  suppress, a differing byte marks, `seedServed` suppresses the first save.
- A live-chunk parity gametest: for generated chunks, the native body of `nativeColumn` translates
  to exactly the bytes `serializeColumn` returns (the split cannot drift).
- `IdentityDictionaryTest`: a remembered identity skips the parse (counted), an invalid one throws
  twice, the bound holds, two threads agree.
- **Shadow run on the rig** (one-off, instrumented build): during the 40 blocks/s flight both the
  old decision (FNV over v20) and the new one are computed for every event; they must agree on
  every event.
- Soaks: `dirty-broadcast`, `cold-restart-resync`, `store-save-storm`, `fresh-backfill`,
  `warm-rejoin`.
- Measurement: the flight profile before and after (LSS share of the server thread, ms per tick).

## 2. Generation bounds

### Evidence

Defaults: generation on, 512 chunks, 40 concurrent. Around a player in ungenerated terrain the
server generated 55 columns a second at about 1.3 cores; a fresh 512-chunk disc is 5.3 hours,
9.2 GB of world and 8.0 GB of store. With a world border 512 blocks wide and a player inside it,
2,096 chunks were generated in about 70 seconds where 1,089 fit inside the border.

### Approaches

- **Refuse at the ticket** (main thread, where the border lives): a refused position still takes
  a generation slot for a round trip, and it waits behind the pacing gates, so a far ring that
  will never be generated is answered only as fast as the near work drains. Rejected.
- **Refuse at the miss** (processing thread), chosen: the answer goes out in the same cycle and
  no ticket exists. It needs the border published to that thread.

### Design

A miss becomes a generation ticket in two places: `OffThreadProcessor.handleDiskNotFound` and the
miss-memo rung of `IncomingRequestRouter.tryAdmitAndSubmit`. Both ask
`GenerationPolicy.allows(dimension, cx, cz, playerChunk)` first.

**A refusal** is answered `ColumnNotGenerated`: the disposition a generation-disabled server
already gives, with the same accounting (soak law A5: a miss answered not-generated). The client
stops asking for that position; existing terrain beyond it is still served; a dirty broadcast
revives it when the chunk appears. A refused miss writes no memo, and the memo rung does not
speak for a refused position (it falls through to the disk read), the rule a generation-disabled
server already follows.

The policy has three parts:

1. **The world border.** Each tick the main thread compares every dimension's border with the
   one it published and, when one differs, replaces an immutable `GenerationBounds` behind a
   volatile field on the processor. The test is vanilla's own (`WorldBorder.isWithinBounds`: the
   chunk overlaps the border's area). Outside it nothing is generated unless
   `generation.outside_world_border` is true. Default: **false**.
2. **A radius.** `generation.distance_chunks`: 0 (the default) means the LOD distance, as today.
   A smaller value generates only within that many chunks (a square, like the LOD distance) of
   the requesting player. A player whose position is not known yet is not refused.
3. **Free disk.** Below 2 GiB free on the world's volume (the backfill's floor), no new ticket.
   Read on the processing thread at most once every five seconds; a failed reading refuses
   nothing. One WARN when it starts and one line when it ends.

**Coming closer.** A position refused for distance must become askable when the player comes
closer, and the client never asks again on its own. So when a player's chunk changes while a
radius is in force, the processing thread takes the positions that entered the radius (inside
the new square, outside the old one), keeps those the policy now allows and that have no
done-bit (a done-bit means the position was answered with content this session), and sends that
player a dirty notice for them. The client revives a parked position on a dirty notice
(`ColumnStateMap.markDirtyIfKnown`) and ignores one it has no record of. Nothing is remembered
per refusal: on a generated world every entering position has its done-bit and no notice is
sent. The same pass over the whole square runs once when the border grows or the disk recovers.

The notice travels to the main thread on a queue beside the send actions and goes out through
each platform's existing dirty sender; it does not touch the dirty tracker, the store or the
timestamp cache.

`/lsslod diag` gains the refusals on its Generation line: `refused border=… distance=… disk=…`.

### Settings

```yaml
generation:
  enabled: true
  #distance_chunks: 0 # Generate only this close to a player; 0 = the LOD distance.
  #outside_world_border: false # Also generate terrain outside the world border.
```

Both are commented in the template, like `service.show_permission_refusal`: 0.23 and older refuse
a file with a key they do not know, so a fresh file must still load there. A file gains the key
only when the setting is changed.

### Per platform

The decision is in `common`. Fabric, NeoForge and Sponge publish the border from
`ServerLevel.getWorldBorder()` in the shared service; Paper from its own service. The notice
needs a per-player dirty send on each: both services already have one.

### Tests

- `GenerationPolicyTest` (common): the border test against vanilla's rule at the edges (a border
  on a chunk boundary, inside a chunk, negative coordinates); the radius; the disk floor; an
  unknown dimension and an unknown player position refuse nothing.
- Router and processor tests (common): a miss outside the border answers not-generated with no
  ticket and no memo; a memo entry written for another player does not answer for a refused one;
  inside is unchanged; each setting turns its rule off; the disk floor with an injected reading.
- `GenerationRevivalTest` (common): the entering positions for a one-chunk step, a diagonal
  step and a jump larger than the radius; positions with a done-bit and positions outside the
  border are left out; nothing is sent when the radius is the LOD distance.
- A Fabric gametest: border set, a request beyond it for an ungenerated position is answered
  not-generated and no chunk is generated; the existing generation gametests unchanged.
- Live on the rig: the border run of the findings pass again (expect no chunk outside the
  border), and a radius run on fresh terrain (terrain appears as the player flies).

## 3. Columns are deflated twice

### Evidence

85 % of the network thread's samples in a warm fill are `Deflater.deflateBytesBytes`; 0.054 ms a
column measured alone; the output is 0.14 % larger than the input. A prototype that skipped the
compressor cut the network thread from 5.9 % to 1.0 % of a core at 712 columns a second.

### Approaches

- **A frame marked "not compressed"** (a zero length prefix), as in the prototype. The vanilla
  decoder accepts it for any size. **Velocity and Krypton do not:** both refuse an uncompressed
  frame at or above the threshold (`MinecraftCompressDecoder`: "Actual uncompressed size … is
  greater than threshold"). A server behind Velocity, or a client with Krypton, would be cut off.
  Rejected.
- **A real zlib stream that stores instead of compressing** (chosen). The frame says the true
  uncompressed length and carries a valid zlib stream made of stored blocks: a two-byte header,
  five bytes per block of up to 65,535 bytes, the data as it is, and the Adler-32 checksum. Every
  conforming inflater reads it. It costs a copy and a checksum, and 11 bytes.
- Lowering the compression level for the connection: one deflater serves the whole connection,
  vanilla chunk packets included. Rejected.

### Design

In `common`, with no netty dependency:

- `StoredDeflate`: writes the stream from one `ByteBuffer` into another.
- `ColumnFrame.isCompressedColumn(ByteBuffer)`: true only for a packet that is one id byte, the
  identifier `lss:voxel_column`, and a current-layout column whose codec byte says zstd and whose
  section-array length matches the rest of the packet. A raw column (a client without zstd, or
  an old dialect) is still deflated by Minecraft, as today.

`ColumnPacketPassthrough` (a netty outbound handler, a thin twin in `xplat` and in `paper`) sits
between the packet encoder and the handler named `compress`:

- a compressed column at least as long as the connection's threshold goes out as
  `VarInt(length) + stored stream`, written through the compressor's context so it continues at
  the handler behind the compressor;
- everything else passes untouched.

Installed when a player's LSS session is registered, on the channel's event loop, and only when
the pipeline has the vanilla shape: a handler named `compress` and, toward the socket from it, one
named `prepender`. Anything else (no compression, a stack that merged the two) leaves the
connection as it is. Not installed when `network.skip_double_compression` is false. The check
does not depend on the packet id's value, so ViaVersion's rewritten ids do not matter. A wrong
guess could only ever skip Minecraft's compression for one packet: the bytes the client decodes
are the same either way.

### Settings

```yaml
network:
  #skip_double_compression: true # Send already-compressed columns without compressing them again.
```

Commented in the template, default on, restart to change.

### Tests

- `StoredDeflateTest` (common): `java.util.zip.Inflater` restores the input for lengths 0, 1,
  65,535, 65,536 and 200,000, from heap and direct buffers; the checksum matches
  `java.util.zip.Adler32`.
- `ColumnFrameTest` (common): frames in the current layout with codec zstd and raw, the two old
  layouts, a truncated header, another channel, a two-byte packet id.
- `ColumnPacketPassthroughTest` (Fabric, netty `EmbeddedChannel` with the real vanilla
  `CompressionEncoder`, `CompressionDecoder` and the real column codec): a compressed column
  reaches the decoder's output byte for byte and is larger on the wire than its payload by the
  framing only; a raw column, a small column and another packet are deflated as before;
  reference counts balance; a pipeline without `prepender` is left alone.
- The Velocity and Krypton rule as an assertion: the declared length is the true length and at
  least the threshold.
- Real-stack rows with the setting on (it is the default), Paper included.
- **A real Velocity proxy** in front of the rig server with backend compression on, the
  development client through it: columns arrive, no disconnect.
- Measurement: the warm fill at the default cap and at 100, before and after.
- Soak law A2 (bytes received equal bytes sent) in every soak of this plan.

## 4. The default cap

`network.bandwidth.per_player_mib_per_second` is 25 and counts uncompressed bytes: about 4.2 MB/s
on the wire, 712 columns a second, 24 minutes for a 512-chunk disc. At 50 the request pipeline
delivers about 1,480 columns a second, 12 minutes. With §3 that costs the server less CPU than a
fill does today. The global cap (75) is not changed, so the server's peak is the same; one player
alone may use two thirds of it where today it is one third.

No code in this plan. Existing files keep the value written in them; only new installs would
see a new default. **Decision for VoX**, with the measured table from §3's runs.

## 5. Store pages

New stores are created with 32 KB pages (16 KB today). Rows average 5.9 KB; the same rows take
12 % less disk and read as fast in fill order (7.7 µs against 8.4 µs). An existing store keeps
its page size: the cap arithmetic already reads it from the file. 64 KB saves 17 % but random
reads cost 4 µs more; not chosen.

The compression level stays 1: level 3 is 3.3 % smaller for 7 % more CPU at every deposit, and
server CPU is what this release is about.

Tests: a new store reports 32,768; a 16 KB store still opens, serves and evicts (the migration
test creates one). Live: backfill the rig's world into a new store and compare the file size and
the writer thread's CPU with the 16 KB numbers of the findings pass.

## 6. #380: the map turned on after the download

### Evidence

A player downloads the terrain with Voxy while no map is being written (the setting is off, the
map mod is not installed yet, or the server asked for no map ingestion). Later a map is written.
The cache says every column is current, the server answers "up to date" without data, and the
client keeps no column data of its own: the map stays empty until Re-download Terrain, which
also makes Voxy take everything again. The reverse case (map first, Voxy later) has had a marker
since 0.18. VoX on the issue: "I need a better user experience for this."

Nothing in the client is per consumer today: a column counts as delivered for everyone once any
consumer took it, and a map that is off drops it silently.

### Approaches

- **A marker on the whole cache** ("this cache has fed a map"): cannot record a fill that is half
  done. Written early it strands the rest; written when complete it never is, because the cache
  keeps columns far outside the current range.
- **Ignore the cache when a map appears:** an automatic Re-download Terrain. Voxy takes every
  column again, and each off-and-on costs a whole download.
- **Read the terrain back out of Voxy's storage:** no server cost, but deep reflection into a
  mod that is All Rights Reserved and changes its storage between versions.
- **A debt per column** (chosen): the client remembers which columns it holds that no map has
  seen, and asks the server for exactly those again when a map is being written.

### Design

Client only; no server, wire or protocol change.

- **The debt.** One more mask in the column state (`mapOwed`), which the scanners do not read.
  A column that arrives while no map is being written sets its bit; one that arrives while a
  map is being written clears it. "Being written" is one predicate (`ModCompat.isMapWriting()`):
  a map backend is registered and enabled, its session is active, the server allows it, and it
  is not inert.
- **On disk.** A sidecar next to the cache file (`<dimension>.mapowed`), read and merged with it.
  The cache file's own format does not change, so 0.23 still reads it. No sidecar means nothing
  is owed, except: a session without a map that saves a cache with no sidecar marks every held
  column owed (the columns were downloaded before this release, and no map is seeing them).
- **Asking.** When the normal scan has asked for everything it wants and budget is left, the
  request manager adds owed columns (held, in range, not already in flight) to the batch as
  plain requests without a timestamp, which the server answers with data. The fill never
  displaces a normal request.
- **Routing.** An answer for an owed column whose timestamp equals the one held goes to the map
  consumers only: Voxy already has exactly that column. Any other timestamp is new content and
  goes to everyone. A map that fails such a delivery keeps the debt and leaves the cache alone.
- **Telling the player.** One line when a fill starts ("Filling the map from the server: N
  columns"), the cost in the setting's tooltip (en, zh_cn, zh_tw), and a status reason while it
  runs.

Not covered: singleplayer and LAN hosts (the map mod maps the world itself), cave layers, and a
map whose own data was deleted (Re-download Terrain remains for that).

### Tests

- `ColumnStateMapTest`: the bit is set and cleared at receive, survives pruning rules like the
  stamps, and is not a classification input (`SectionStateFuzzTest` and
  `QuadtreeWalkDifferentialTest` unchanged).
- `ColumnCacheStoreTest`: the sidecar round trip, merge on save, the no-sidecar rules for a
  session with and without a map, deletion with the cache.
- `LodRequestManagerTickTest`: owed columns are added only after the normal wants, never above
  the budget, never while in flight, only on a current-protocol remote session.
- `LSSApiDispatchTest`: the map-only audience; `VoxelColumnReceiverTest`: equal stamp goes to
  maps only, another stamp to everyone.
- A client gametest or soak: download with the map off, reconnect with it on, the map consumer
  receives the columns and the Voxy consumer receives none of them twice.
- Real stack: the Xaero row, map turned on after a fill.

## 7. #429: black strips with the border fill, and a counter for the next report

### Evidence

NeoForge 1.21.1 with a Voxy backport and ScalableLux on the client: black strips near the edge
of the render distance, gone with `lod.voxy_border_fill` off (the reporter's test). The border
fill hands vanilla-loaded chunks at the edge to Voxy. `lightReady` checks that the chunk's light
is switched on and that each section's light type is "light and data"; it never looks at the
data. Voxy then reads each section's sky light from the light engine and stores a missing layer
as 0. ScalableLux 0.1.0.1 (checked in its bytecode) reports "light and data" as soon as the
packet's light is attached, while its sky-light reader returns null until the client's light
pass has built the chunk's emptiness map. The fill's tick pump can run between the two, and a
chunk Voxy accepted is never submitted again.

Black terrain has now been reported three times with three causes (#382, #383, #429), and
nothing in a report shows whether sections reached Voxy without sky light.

### Design

- **The fix.** `lightReady` gains one more condition, in dimensions with sky light: for every
  section that is not all air, the sky layer Voxy is about to read is not null. Vanilla always
  has that layer for a "light and data" section, so nothing changes there. A chunk that is not
  ready is skipped and looked at again on the next pump, as today; there is no deadline, because
  a hand-over is permanent and a late one stores darkness for good, while a gap closes by
  itself. The retry-due test moves ahead of `lightReady`, so a chunk Voxy refused is not probed
  every frame.
- **Counters** in `/lss diag` and the diagnostic export, on a new line after `Light:`: sections
  handed to Voxy without sky light at or above the column's highest block in a sky dimension
  (server columns and Distant Horizons columns), and border-fill chunks held back because their
  sky light was not readable yet. A report with the first number above zero points at the data;
  at zero, at the renderer.
- Only submitting from the render-end pump was considered and rejected: NeoForge fires that
  event on frames that ran no light pass too.

### Per line

1.21.1 has the same file with four flavour differences (it is on the adapted list); the probe is
the same call. The fix matters most there.

### Tests

- `VoxyVanillaCoverageTest`: a chunk whose sky layer is null is not submitted and is submitted
  once the layer exists (red without the fix); a dimension without sky light is not held back;
  an all-air section with no layer does not hold a chunk back; a refused chunk is not probed
  before its retry is due.
- `VoxyCompatTest`: the counter counts a null sky layer at or above the highest block, not one
  below it, and nothing in a dimension without sky light.
- `ClientColumnProcessorTest` and the diagnostics tests: the new line and the export fields.
- No real-stack row has ScalableLux on a client with Voxy. The reporter is asked to try a build.

## 9. Wire and protocol impact

None. §3 changes how one packet is framed for Minecraft's own compression layer, within what
that layer already accepts. §2 uses the existing not-generated answer and the existing dirty
notice.

## 10. Risks

- §1: a hash over different bytes could disagree with the old one in some case nobody thought
  of. The shadow run is the answer to that.
- §2: a border-limited server stops showing LOD terrain beyond its border unless it was already
  generated. That is the point, and one setting restores it. The revival notice is new traffic:
  about 2R + 1 positions per chunk travelled.
- §3: a stack that reads frames before the compressor's context and breaks on a handler it does
  not know. One setting turns it off.
