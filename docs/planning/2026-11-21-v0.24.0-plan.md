## 1. The server thread's cost per chunk load and save (Fabric, NeoForge, Sponge)

### Evidence

`DirtyContentFilter` decides at every chunk save whether LOD-visible content changed, and seeds
its baseline at every chunk load. Both run on the server thread. Each call serialized the live
chunk, translated the bytes to the served (v20) layout and hashed the result with a
byte-at-a-time FNV-1a 64.

With one player flying at 40 blocks a second (about 107 saves and 77 loads a second) LSS code
was on the stack in 21 % of the server thread's busy samples: the hash, the translation (a third
of it parsing block-state names again for every column), the serialization and its buffer.

A second question was checked and closed: about a third of the saves in that flight are marked
changed. A diagnostic that compares the load-time bytes with the first save's showed real
differences (blocks in most, block light in the rest): vanilla's post-processing of chunks that
were pregenerated and never loaded. Not a seeding fault. Nothing to fix.

### Design (as built)

1. **Hash the native body, not its translation.** Every baseline and every comparison reads a
   live chunk through one serializer seam: the save hook, the load seed and the generation serve
   (`seedServed`, which reads the chunk in the same server-thread task as the serve). The
   translation is a pure function of the native bytes and loses nothing (indexed containers keep
   their packed longs and get their palette values renamed through a one-to-one table; direct
   ones are re-palettised from the same ids), so equal native bodies mean equal served bytes and
   the other way round.
2. **A fast hash**: `ContentHash64`, the XXH64 algorithm, 1.8 µs for a 35 KB column where FNV-1a
   took 28 µs. In memory only; nothing persistent changes.
3. **No buffer churn**: the body is written into a per-thread scratch buffer (guarded against
   re-entry) through `SectionSink`, which writes a long array as one block, and hashed in place.
4. **Validated names are remembered**: `IdentityDictionary` parses an identity once per process,
   not once per column (bounded at 131,072 strings; a failure is never remembered). This no
   longer matters to loads and saves; it is for the serves that still translate (memory probes
   on the server thread, cold reads and the backfill off it).

### Numbers

The same never-loaded corridor, restored before each run; one player, 40 blocks a second for a
minute; about 6,400 saves and 4,600 load seeds in each run.

| Build | LSS on the server thread's stack | Server thread, whole |
| --- | --- | --- |
| 0.23.0 | 0.80 s per minute | 8.3 % of a core |
| native body, fast hash, memo | 0.47 s | 7.5 % |
| plus scratch buffer and bulk writes | 0.37 s | 7.2 % |

A shadow build that computed the old decision beside the new one for every save agreed on all
6,000 it logged (1,925 changed, 4,075 unchanged, none on one side only).

**Acceptance:** LSS's share of the server thread in that flight at or below 0.45 s per minute in
two runs of the final build, against 0.80 s; the shadow count of one-sided decisions is 0; the
suppression counts of the `cold-restart-resync` and `dirty-broadcast` soaks are unchanged.

### What stays pinned

A serve seeds the baseline; a probe serve does not; `newlyGenerated` chunks are not seeded at
load; all-air hashes to the sentinel; LRU eviction; `forget`; fail-open on an error. The store's
own content hash (CRC32C, persistent) is not touched.

### Next, not in this release

What is left is vanilla's own `section.write` and the light lookups. The saves could leave the
server thread: vanilla copies the chunk for its asynchronous write, and the hash could run on
that copy from inside the write task (not beside it: two threads in one `PalettedContainer` trip
vanilla's threading detector and would fail the save). That means moving the hook once more, and
its place was chosen for C2ME and Moonrise (#69); it needs both checked first. The load seed has
no such copy.

## 2. Generation bounds

### Evidence

Defaults: generation on, 512 chunks, 40 concurrent. Around a player in ungenerated terrain the
server generated 55 columns a second at about 1.3 cores. With a world border 512 blocks wide and
a player inside it, 2,096 chunks were generated in about 70 seconds where 1,089 fit inside the
border: an operator who set a border to bound the world gets (R + 512)² chunks. Nothing looks at
free disk space except the store's backfill.

### Design

Two rules, both decided where a miss becomes a generation ticket
(`OffThreadProcessor.handleDiskNotFound`, and the miss-memo rung of
`IncomingRequestRouter.tryAdmitAndSubmit`).

**The world border.** No generation for a chunk that lies wholly outside the world border.

- The test is overlap, our own rule: a chunk any part of which is inside the border is
  generated. (Vanilla's `WorldBorder.isWithinBounds(ChunkPos)` asks for the whole chunk inside;
  that would leave the edge chunks players stand in ungenerated.)
- The main thread publishes each dimension's border as a rectangle of chunks, behind a volatile
  field on the processor, replaced only when it changed. While a border is moving it publishes
  the larger of the current and the target size, so a moving border is one change, not one a
  tick. A dimension that was never published has no bound.
- A refused miss is answered `ColumnNotGenerated`, the answer a generation-disabled server gives
  for it: the client moves on to terrain that exists and comes back when a dirty broadcast says
  the chunk has appeared (a player walked there, or the operator pregenerated). Same accounting
  (soak law A5: a miss answered not-generated).
- Only an authoritative miss is refused. A read that failed or timed out, or one an edit
  overtook, says nothing about whether the chunk exists: beyond the border it takes the
  transient drop (no answer, asked again), never the permanent one.
- No memo is written for a refused miss, and the memo rung does not speak for a position outside
  the border (it falls through to the disk read): the rule a generation-disabled server follows.
  The check sits before the memo hit is counted.
- `generation.outside_world_border: true` restores today's behaviour. Restart to change.
- Known limit: when a border grows while players are online, positions they were refused stay
  parked for them until a dirty broadcast, a rejoin, or until they have moved away. Chunks
  generated in the new area (by players or a pregenerator) revive them the usual way.

**Free disk.** Below 2 GiB free on the world's volume (the backfill's floor) generation is held;
it resumes at 3 GiB.

- The processing thread reads the free space every five seconds. A reading that fails holds
  nothing.
- A hold behaves exactly like `generation.enabled: false` set at run time, through the switch
  that already exists for that: misses are answered not-generated, and clients are told that
  generation is off with the session config they already understand. When the hold ends they
  are told it is on again and ask afresh. The platforms only mirror the processor's hold into
  the flag they advertise and re-push; the generation service and the settings are untouched.
- The LOD store stops taking deposits below the same floor (today only the backfill does).
- One WARN when a hold starts, one line when it ends, and the state in `/lsslod diag`.

`/lsslod diag` gains, on its Generation line, the chunks generated since start and the refusals
(`outside_border=`), and the hold (`held: low disk`).

### Settings

```yaml
generation:
  enabled: true
  # 0.23 and older do not know the next key and refuse a file that has it.
  #outside_world_border: true # Also generate terrain outside the world border.
```

Commented in the template with its default (false) in code, like
`service.show_permission_refusal`; the two places that special-case that one key become a list.

Upgraded servers with a border change behaviour: LOD view ends where generated terrain ends.
That is what a border means, and the release notes lead with it.

### Per platform

The decision is in `common`. The shared service (Fabric, NeoForge, Sponge) and Paper's service
each publish the borders from their tick and mirror the hold; on Folia the service ticks on the
global region, which is where the border lives.

### Tests

- `GenerationBoundsTest` (common): overlap at the edges (a border on a chunk boundary, inside a
  chunk, negative coordinates, a border narrower than a chunk), an unpublished dimension, the
  moving-border rule.
- Processor and router tests (common): an authoritative miss outside the border answers
  not-generated with no ticket and no memo; a failed read outside the border is dropped, not
  answered; a memo written for an inside position does not answer for an outside one, and no
  memo hit is counted; inside is unchanged; the setting turns the rule off.
- `DiskHoldTest` (common): the floor and the hysteresis with an injected reading; a failed
  reading; the hold flips the processor's generation switch and back, with the terminal reset
  the settings path performs.
- Store: deposits are dropped and counted below the floor and resume above it.
- A Fabric gametest: border set, a request beyond it for an ungenerated position is answered
  not-generated and no chunk appears; the existing generation gametests unchanged.
- Live on the rig: the border run of the findings pass again; expect no chunk generated outside
  the border (2,096 before).
- Soak law A5 in the generation soaks.

## 3. Columns are deflated twice

### Evidence

85 % of the network thread's samples in a warm fill are `Deflater.deflateBytesBytes` (vanilla
compresses at zlib's level 6); 0.054 ms a column measured alone; the output is 0.14 % larger
than the input. A prototype that skipped the compressor cut the network thread from 5.9 % to
1.0 % of a core at 712 columns a second.

### Approaches

- **A frame marked "not compressed"** (a zero length prefix), as in the prototype. The vanilla
  decoder accepts it for any size. **Velocity and Krypton do not:** both refuse an uncompressed
  frame at or above the threshold. Rejected.
- **A real zlib stream that stores instead of compressing** (chosen). The frame says the true
  uncompressed length and carries a valid zlib stream of stored blocks: a two-byte header, five
  bytes per block of up to 65,535 bytes, the data as it is, and the Adler-32 checksum. Every
  inflater reads it, and the vanilla decoder's three checks hold (length at least the threshold,
  at most 8 MiB, inflated size equal to the declared one). It costs a copy, a checksum and 11
  bytes.
- Lowering the compression level for the connection: one deflater serves the whole connection,
  vanilla chunk packets included. Rejected.

### Design

In `common`, with no netty dependency: `StoredDeflate` (writes the stream from one `ByteBuffer`
into another) and `ColumnFrame.isCompressedColumn` (true only for a packet that is one id byte,
the identifier `lss:voxel_column`, and a current-layout column whose codec byte says zstd, whose
section-array length matches the rest of the packet and whose section bytes start with the zstd
magic number). A raw column is still deflated by Minecraft, as today.

`ColumnPacketPassthrough`, a netty outbound handler in `xplat`:

- installed with `addAfter("compress", …)` when a player's LSS session is registered, so it
  sees a packet after the encoder and after anything a protocol translator put there, and just
  before the compressor;
- on every write it looks at the handler named `compress`: only if that is vanilla's
  `CompressionEncoder` does it act, with that encoder's current threshold. A stack that
  replaced the compressor (Krypton on the server) is left alone;
- a compressed column at least as long as the threshold goes out as `VarInt(length) + stored
  stream`, written through the compressor's context so it continues at the length prepender;
- if building the frame fails, the original packet takes the normal path;
- everything else passes untouched.

No settings key. `-Dlss.skipDoubleCompression=false` turns it off for a beta that meets a stack
nobody tried, and `serialization.compressed_columns: false` already switches compressed columns
off altogether.

### Platforms

Fabric, NeoForge and Sponge through the shared handler. **Paper is not built yet**: its
compressor is Velocity's native one, not the JDK's, so the saving there is not the measured one.
Measure first (§8).

### Tests

- `StoredDeflateTest`, `ColumnFrameTest` (common, built): the JDK's inflater restores every
  length, from heap and direct buffers; the recogniser against current, raw, older and
  truncated layouts and hostile length fields.
- `ColumnPacketPassthroughTest` (Fabric, netty `EmbeddedChannel` with the real
  `CompressionEncoder`, `CompressionDecoder` with validation on, and the real column codec): a
  compressed column reaches the decoder's output byte for byte, with the true length and a
  frame that is the payload plus the framing; a raw column, a small column and another packet
  are deflated as before; reference counts balance; a pipeline whose `compress` is another class
  is left alone; a compressor removed after install is survived; a failing frame falls back.
- Live: the development client through a real **Velocity** proxy with backend compression on;
  a client with **Krypton** if it has a 26.3 build; **ViaVersion** on the server (the test
  server's own setup).
- Real-stack rows on the gate jars (the path is on by default).
- Measurement: the warm fill at the default cap and at 100, before and after, same client.
  **Acceptance:** the server's network thread at or below 2 % of a core at the default cap
  (5.9 % before), every column decoded, soak law A2 (bytes received equal bytes sent) green.

## 4. The default cap stays

`network.bandwidth.per_player_mib_per_second` is 25 and counts uncompressed bytes: about 4.2
MB/s on the wire, 712 columns a second, 24 minutes for a 512-chunk disc. Raised, the request
pipeline delivers about 1,480 a second.

Not changed here: the 12-minute figure is from the renderer-less client on loopback, a cold fill
at double the rate was not measured, and changing the cap beside §3 would make the beta's CPU
result impossible to attribute. An operator who wants faster fills has the key; #365 is answered
with it. Revisit after §3 has shipped, with a real Voxy client.

## 5. Store pages: measure the other side first

The same rows in 32 KB pages take 12 % less disk than in 16 KB pages, and read as fast in fill
order from a warm page cache. Before the page size of new stores changes, three things the
findings pass did not measure:

- random reads with the file out of the page cache (a hosted server does not hold an 8 GB store
  in memory);
- the write side: a re-deposit after an edit writes a whole page to the WAL, and the checkpoint
  threshold and the vacuum budget are sized for 16 KB;
- a real backfill, not a sequential rebuild.

If all three are neutral or better, new stores get 32 KB pages (existing ones keep theirs; the
cap arithmetic reads the size from the file) with the vacuum budget derived from the page size.
Otherwise it stays, with the numbers recorded. The compression level stays 1.

## 6. #380: the map turned on after the download

### Evidence

A player downloads the terrain with Voxy while no map is being written (the setting is off, the
map mod is not installed yet, or the server asked for no map ingestion). Later a map is written.
The cache says every column is current, the server answers "up to date" without data, and the
client keeps no column data of its own: the map stays empty until Re-download Terrain, which
also makes Voxy take everything again. VoX on the issue: "I need a better user experience for
this."

### Approaches

- **A marker on the whole cache**: cannot record a fill that is half done.
- **Ignore the cache when a map appears**: an automatic Re-download Terrain.
- **Read the terrain back out of Voxy's storage**: deep reflection into a mod that is All Rights
  Reserved and changes its storage between versions.
- **Fill automatically whenever the client knows the map is behind**: the best experience, but
  it is load the server did not ask for, and a server that stops asking for no map ingestion
  would have every map client download its disc at once.
- **A debt per column, filled when the player asks** (chosen).

### Design

Client only; no server, wire or protocol change.

- **The debt.** One more mask in the column state (`mapOwed`), which the scanners do not read.
  A column that arrives while no map is being written sets its bit; one that arrives while a
  map is being written clears it. "Being written" is one predicate: a map backend is registered
  and enabled, its session is active, the server allows it, and it is not inert.
- **On disk.** A sidecar next to the cache file, read and merged with it. The cache file's own
  format does not change, so 0.23 still reads it. No sidecar means nothing is known to be owed.
- **Fill Map.** A button beside Re-download Terrain, and `/lss fillmap`. It asks the server
  again for the columns the map is owed (or, for a cache from before this release, for every
  column held) and gives the answers to the map only. It resumes after a reconnect and never
  displaces a normal request: owed columns ride in a batch only when the scan has nothing else
  to ask.
- **Routing.** An answer for an owed column whose timestamp equals the one held goes to the map
  consumers only: Voxy already has exactly that column. Any other timestamp is new content and
  goes to everyone. A column answered up-to-date, not-generated or rejected is not asked again.
- **Telling the player.** When a session starts with a map being written and columns owed, one
  chat line with the count and the action. The setting's tooltip names it. en, zh_cn, zh_tw.

Not covered: singleplayer and LAN hosts (the map mod maps the world itself) and cave layers.

### Tests

- `ColumnStateMapTest`: the bit at receive, with pruning, and that it is not a classification
  input (`SectionStateFuzzTest` and `QuadtreeWalkDifferentialTest` unchanged).
- `ColumnCacheStoreTest`: the sidecar round trip, merge on save, deletion with the cache.
- `LodRequestManagerTickTest`: owed columns only after the normal wants, never above the budget,
  never while in flight, only while a fill is active, never again after a terminal answer.
- `LSSApiDispatchTest`, `VoxelColumnReceiverTest`: the map-only audience; equal stamp to maps
  only, another stamp to everyone.
- Owed stays 0 across a normal join with a map on.
- A soak or gametest: download with the map off, reconnect with it on, Fill Map, the map
  consumer receives the columns and the Voxy consumer none of them twice.

## 7. #429: black strips with the border fill, and counters for the next report

### Evidence

NeoForge 1.21.1 with a Voxy backport and ScalableLux on the client: black strips near the edge
of the render distance, gone with `lod.voxy_border_fill` off (the reporter's test). The border
fill hands vanilla-loaded chunks at the edge to Voxy. `lightReady` checks that the chunk's light
is switched on and that each section's light type is "light and data"; it never looks at the
data. Voxy then reads each section's sky light from the light engine and stores a missing layer
as 0. ScalableLux 0.1.0.1 (checked in its bytecode) reports "light and data" as soon as the
packet's light is attached, while its sky-light reader returns null until the client's light
pass has built the chunk's emptiness map. The fill's tick pump can run between the two, and a
chunk Voxy accepted is never submitted again.

Black terrain has now been reported three times with three causes (#382, #383, #429), and
nothing in a report shows whether sections reached Voxy without sky light.

### Design

- **The fix.** `lightReady` gains one more condition, in dimensions with sky light: for every
  section that is not all air, the sky layer Voxy is about to read is not null. Vanilla always
  has that layer for a "light and data" section, so nothing changes there. A chunk that is not
  ready is skipped and looked at again on the next pump, as today; there is no deadline, because
  a hand-over is permanent and a late one stores darkness for good, while a gap closes by
  itself. The retry-due test moves ahead of `lightReady`, so a chunk Voxy refused is not probed
  every frame.
- **Counters** in `/lss diag` and the diagnostic export, on a new line after `Light:`: sections
  handed to Voxy without sky light at or above the column's highest block in a sky dimension
  (server columns and Distant Horizons columns); border-fill chunks held back for sky light,
  as a count since joining and as a gauge of how many are waiting now and for how long the
  oldest has waited (with no deadline, a stuck hold must be visible).
- Only submitting from the render-end pump was considered and rejected: NeoForge fires that
  event on frames that ran no light pass too.

### Per line

1.21.1 has the same file with four flavour differences; the probe is the same call. The fix
matters most there.

### Tests

- `VoxyVanillaCoverageTest`: a chunk whose sky layer is null is not submitted and is submitted
  once the layer exists (red without the fix); a dimension without sky light is not held back;
  an all-air section with no layer does not hold a chunk back; a refused chunk is not probed
  before its retry is due; the gauge and its age.
- `VoxyCompatTest`: the counter counts a null sky layer at or above the highest block, not one
  below it, and nothing in a dimension without sky light.
- The diagnostics tests: the new line and the export fields.
- No real-stack row has ScalableLux and Voxy on one client; the reporter is asked to try a
  build.

## 8. Not built, with reasons

- **A generation radius** (generate only near players). It bounds nothing by default, and a
  refusal for distance must be taken back as the player comes closer and when someone else
  generates the chunk: per-player bookkeeping, a notice path on every platform and a soak law of
  its own. The border and the disk floor fix what was measured as wrong; whether LOD generation
  should have a smaller reach by default is a product decision that deserves its own plan.
- **The compression bypass on Paper.** Unmeasured: Paper compresses with Velocity's native
  library. Measure a warm fill on a Paper 26.3 server first.
- **A higher default bandwidth cap** (§4) and **a settings key for the bypass** (§3).
- **zstd level 3 for the store**: 3.3 % smaller for 7 % more compression time; too small to
  touch a stored format's writer for.
- **Hashing saves off the server thread** (§1, "Next").
- **Filling the map automatically** (§6).

## 9. Per-line differences

Implemented on main (26.3). 1.21.1 follows through the line tool after main has the change;

None. §3 changes how one packet is framed for Minecraft's own compression layer, within what

## 12. As built

### §1 The change detector (commits `3fb1e2eb7`, `a52f68c1a`)

`SaveObservation` no longer hands out bytes (the save-hook deposit went delete-only in the R2-M2
round); the hash path no longer counts masked sections (a hash is not a serve).

### §2 Generation bounds (commits `395ad9019`, `8e1329db0`)

- The border rule is LSS's own (a chunk is inside when it overlaps the border square; vanilla's
  chunk test is containment), published once a second per dimension as chunk rectangles
  (`GenerationBounds`), over the larger of the border's size and its lerp target. A miss outside
  it is answered "not generated" only when the miss is authoritative; a failed or timed-out read
  is dropped and asked again. No miss memo is written for it and the memo does not speak for it.
- `generation.outside_world_border` (default off, read at start; a commented key in the
  templates, so 0.23 still loads the file). Folia publishes the same rectangles from its global
  tick; Sponge through the shared service.
- Low disk: generation is held below 2 GiB free on the world's volume and released at 3 GiB
  (readings every 5 s on the processing thread), by the switch `generation.enabled: false` uses,
  and the session config tells clients so. Store deposits stop below the same floor on the
  store's volume. `/lsslod diag` shows `outside_border=N` and `ON HOLD: low disk`.
- Measured on the rig, fresh terrain, a border 512 blocks wide, one player inside it: 0.23.0
  generated 2,912 chunks in about 110 s and kept going (worldgen workers 78 % of a core); the
  candidate stopped at 656 (`outside_border=109437`, workers 8.5 %).
- The hold, live, with a simulated reading (`-Dlss.soak.freeDiskFile`): generation went 1,673,
  held at 1,793 for 40 s (also at 2.5 GiB, between the two marks), resumed to 3,313. The store
  dropped 139 deposits and reported `low-disk`; the client logged the session config at the
  start and at the end of the hold.

### §3 Double compression (commit `9770292db`)

- A handler behind `compress` writes a compressed column packet as `VarInt(length)` plus a zlib
  stream of stored blocks (`StoredDeflate`): the frame every decoder accepts for any size. The
  zero-prefix "not compressed" frame of the prototype is refused by Velocity and Krypton above
  the threshold. It acts only when `compress` is vanilla's `CompressionEncoder`, reads the
  threshold per write, and recognises a column by its full current layout and the zstd magic
  (`ColumnFrame`). `-Dlss.skipDoubleCompression=false` turns it off. Fabric and NeoForge; Paper
  is not built (its compressor is Velocity's native one: measure first).
