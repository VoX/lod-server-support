# LSS 0.24.0-beta.1 release preparation

Prepared 2026-11-23 on branch `release/v0.24.0-beta.1`, after the 0.24.0 changes merged into main (#431, #432).
The beta goes to the two full-tier lines, 26.3 and 1.21.1
([decision 0002](../decisions/0002-beta-first-releases.md)). Identities, counts and jar hashes are
in the [manifest](../implementation/2026-11-23-v0.24.0-beta.1-release-preparation.json). Notes:
`v0.24.0-beta.1-release-notes/` (one file per line).

## Scope

[Plan and as-built record](2026-11-21-v0.24.0-plan.md), with every review and its fold in §11.

- **Less work on the server.** Noticing which chunks changed at load and save takes about a third
  of the server-thread time it did (Fabric, NeoForge, Sponge). Terrain that is already compressed
  is no longer deflated again on its way out (the same three; not Paper).
- **Generation is bounded.** It stops at the vanilla world border unless
  `generation.outside_world_border` is set, and it holds while the world's disk has under 2 GiB
  free (`-Dlss.lowDiskHoldMiB`).
- **#429:** Voxy's border fill waits for sky light it can read.
- **#380:** the client records what a map mod was never given; **Fill Map** (a button and
  `/lss fillmap`) has the server send it once more, and `/lss fillmap stop` takes that back.

Decided by the maintainer, and VoX can flip any of them: the border rule is on by default; no
generation radius; the bandwidth cap stays 25 MiB/s; Fill Map never starts by itself, and one
press stands until the cache owes the map nothing; the two off-switches are JVM flags.

## Reviews

fill and a fourth read before its merge. Then, for this release: three reviewers over everything
since 0.23.0 (server failure cases, the decisions and upgrade paths, the 1.21.1 port), and one

checked in the code; plan §11 has the tables and what was deliberately left alone.

Each rule has a test that one deliberate break turns red: 14 for the server side, 117 for the
map fill, 16 and 18 for the two late folds, and on 1.21.1 one per item plus the folds' (20 and
18). Two were equivalent and led to removals (a guard that could not be reached, and three
assignments nothing could observe).

## Fill Map, live

Three sessions per map mod on a real 26.3 server with a pregenerated world (40 chunks): terrain
downloaded with no map (A), the same cache with the map on and one fill (B), and the next join
(C).

- **Xaero's World Map:** A: server sent 6304; client owed 6304, other consumer 6304, xaero wrote 0; B: server sent 0 before the fill, 6304 at the end; delivered 6304, owed 0, failed 0, unwritten 0, without_data 0; other consumer 368; xaero wrote 6304; fill took 35.4 s; C: server sent 0; delivered 0, owed 0.
- **JourneyMap:** A: server sent 6304; client owed 6304, other consumer 6304, journeymap wrote 0; B: server sent 0 before the fill, 6304 at the end; delivered 6304, owed 0, failed 0, unwritten 0, without_data 0; other consumer 368; journeymap wrote 6304; fill took 35.4 s; C: server sent 0; delivered 0, owed 0.

In both: nothing is sent for the map before the request, every owed column is sent once and
written by the map, the other consumer takes only the columns the server restamped, and the next
join downloads nothing.

Not covered by a real run: a press of the button itself (the harness sends the same request),
the stop command, a server without a LOD store, and Voxy's border fill under ScalableLux (the
NeoForge row's client has no Voxy). Unit tests cover the first three; the last waits for the
reporter of #429 and the visual pass.
