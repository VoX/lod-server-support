# 0.23.0 plan

Status: reviewed 2026-11-13 (two reviewers before any code; fold in §9). Nothing here merges to
main before 0.22.0 is tagged (its beta soak ends 2026-11-16 07:26 UTC). Ships as `0.23.0-beta.1`
on 26.3 and 1.21.1 first ([decision 0002](../decisions/0002-beta-first-releases.md)), then
`0.23.0` on 26.3, 1.21.1, 26.2 and 1.21.11.

Theme: **a clear answer when something is wrong.** 0.22.0 taught the client to say why no distant
terrain arrives. 0.23.0 finishes the cases it could not answer and the ones 0.22.0 left to this
release ([0.22.0 plan](2026-11-13-v0.22.0-plan.md) §7):

1. A settings file with a mistake in it: the mod is off, and today only one log line says so.
2. "Share My Position: off" never reaches the server from a client that gets no session.
3. "Switched off here: for everyone, for this world, or for you" cannot say which.
4. A Voxy Server Side player who types `/lss status`, as every document says, gets "unknown
   command".

Before any of it, one question from the research is answered with a real run (§0).

Not built, with reasons in §6: ignoring unknown settings, the VSS server command aliases, the
server answering a version it does not speak, a server chat line for refused players.

Research: two read-only passes over main at `e0208edb3`. Facts below cite code as `file:line` at
that commit.

## 0. First: does a NeoForge client negotiate protocol 20 on a Fabric or Paper server?

**Answered 2026-11-13, on the 0.22.0 gate jars: yes, on both, on the first handshake.**

The question came from the research. On NeoForge a send is dropped without an error while the
loader has not seen the server's channel list (`NeoForgeClientLoaderServices.java:36-38`), and the
handshake goes out at `ClientPlayerNetworkEvent.LoggingIn` (`LSSNeoClientBootstrap.java:48-49`).
The session gate would count a dropped send as sent and arm the discovery ladder
(`ClientSessionGate.java:345-366`), whose next rung, 200 ticks later, announces protocol 19: terrain
ten seconds late, no far players (`ServerReceiverGlue.java:657-665`), no session flags, and a
refusal by a server that asks for no map ingestion. A NeoForge server negotiates channels before
play, so the existing NeoForge row could not show it.

| Server | How it was run | Result |
| --- | --- | --- |
| Fabric 1.21.1 | the new real-stack row `neoforge-client-fabric-server-1.21.1` (production client on a private display) | protocol 20, 2,909 columns in 65 s |
| Paper 1.21.1 (build 133) | one extra visual-pass row on the Windows NeoForge test instance, two joins | protocol 20 both times; the server logged the handshake in the same second as the join; `Dialects: v20=1, v19=0` |

So the channel list is known by `LoggingIn` on all three server kinds, and nothing is fixed. The
silent drop stays in the code as a latent trap: §2 no longer depends on a handshake having been
sent, and the row stays in the matrix so a loader change that opens the gap turns it red.

The real-stack tool still learns to provision a Paper server (§5): three sections below change
Paper-only code.

## 1. A settings mistake is impossible to miss

### What happens today

Any unknown key, wrong type or broken YAML fails the whole file
(`SettingsSchema.java:166-186`, `YamlSettingsCodec.java:283-334`).

- **Server.** One ERROR line at startup: `Server settings unavailable; LOD service remains
  disabled. Repair YAML and restart: <reason>` (`YamlServerConfig.java:48`). The service, the store
  and far players are off until a restart. The line scrolls away, the first problem hides the
  others, and nobody in the game is told.
- **Client.** One ERROR line (`LSSClientConfig.java:49`). Receiving, far players, sharing and map
  writing are off. The status screen prints a line about it, but the verdict above it reads "Off:
  you turned receiving off in the settings", which is false, and `/lss status` in chat has only the
  false line.

### What changes

The file is read as strictly as today, with one exception (§6 says why strict). What changes is
how a mistake is reported.

**The one exception: boolean spellings.** The parser reads YAML with the JSON schema
(`YamlSettingsCodec.java:19-21`), so `enabled: True` or `enabled: yes`, both normal in Bukkit
configuration files, are strings and fail the file. For a key whose type is boolean, the strings
`true`, `false`, `yes`, `no`, `on` and `off` in any letter case are read as that boolean. The
meaning is certain, so nothing is guessed. String keys (`far_players.mode: on`) are untouched.

**All problems, reported after the strict read fails.** The strict path decides whether a file
loads, exactly as today. Only when it has failed does a second pass collect every problem, so
the collector cannot change which files load. A syntax error stays one problem, and a
`config_version` mismatch stops the pass (a newer file would report every key). Each problem has:

- the path, and the line where the parser gives one;
- for an unknown path, at most one suggestion, text only (nothing is loaded from it):
  - a name within two edits in the same group ("did you mean `far_players.mode`?");
  - a setting that exists on the other side ("`far_players.enabled` is a client setting; the
    server's is `far_players.mode`");
  - a pre-YAML name the schema already knows (`requireServicePermission`);
  - otherwise: "If a newer version of the mod wrote this file, delete this line.";
- for a wrong value, what was expected (as today).

Values never appear, as today (`SettingsSchema.java:139`). New: an unknown key under a group that
holds a sensitive setting (`cache`, `far_players`) is printed as `<private>` when it is not a
near match of a known name, because a mis-indented address or player name becomes a key
(`SettingsSchema.java:170`, `:180`) and these lines now reach the status export.

**Server.** Everything names the real file (`settingsPath()`; the VSS file is not
`lss-server-config.yaml`) and the brand's own command.

1. At startup, a block instead of one line:

   ```
   [LSS] lss-server-config.yaml has 2 problems, so the mod is switched off:
   [LSS]   line 41: unknown setting far_players.enabled. That is a client setting; the server's is far_players.mode.
   [LSS]   line 12: service.require_permission must be true or false
   [LSS] Fix the file and restart the server. The file was not changed.
   ```

2. The same block once more after the server has finished starting, so it is the last thing in
   the log. Fabric, NeoForge and Sponge read the file at class load and again at server start
   (`LSSServerConfig.java:9-11`), so the count is pinned: at most two blocks per start on every
   platform.
3. On a dedicated server, one line in chat to each player with the admin right, the first time
   they are seen online in this server run: `[LSS] Switched off: the settings file has 2
   problems. Run /lsslod to see them.` It comes from a small poll (every 100 ticks, the player list
   against a set of players already told), so no platform needs a new join listener, and
   permissions that load late are covered. The admin right is what the command checks: permission
   level 2 on Fabric and NeoForge, `<brand>.admin` on Paper and Sponge. Never in singleplayer or
   on a LAN host (there is no console to send the player to, and no service).

`/lsslod` with no arguments, `/lsslod diag` and a failed `/lsslod reload` start with the block. A
reload that fails on a running server keeps the active settings, as today, and prints the whole
list.

The poll runs while the service is disabled. A service object exists after a failed startup on
all four dedicated platforms, and its tick returns at once (`RequestProcessingService.java:926-927`;
Paper `PaperRequestProcessingService.java:1943-1945`): the announcer is called before that return.

**Client.** New `ClientVerdict.SETTINGS_BROKEN`, checked first (while the file is broken nothing
else the status says matters):

- status: "Off: this mod's settings file has a problem, so the mod is switched off and asks
  servers not to share your position. Fix `<file name>` and restart the game. Deleting it also
  works, but resets every option, including Share My Position." Then the problem lines. The file
  name is the real one (the VSS client's differs).
- chat: "This mod is switched off: its settings file has a problem. /<command> status shows what
  to fix." Once per game start, on the first join, with no counter file. The mod is off on every
  server, the player can fix it, and a second breakage next year must not be silent.

The status snapshot gains one trailing field (the problem lines; empty when the file loaded). The
separate `lss.settings.inactive` line on the status screen goes away.

**The experimental file.** A broken experimental file is ignored whole with one WARN
(`YamlSettingsCodec.java:79-88`), which silently restores defaults, for example the Distant
Horizons source for a player who had switched it off. The status gains a line for it: "The
experimental settings file has a problem and is being ignored: `<file name>`." No verdict, no
chat line: the mod is working.

**Not changed.** What the mod does with a broken file, the clamp-and-report rule for
out-of-range numbers, missing keys taking defaults, "reads never rewrite", the bytes of every
file.

### Tests

- Schema: every file the strict path accepted or rejected before is still accepted or rejected
  (the existing pins, unchanged), except the boolean spellings; three mistakes give three problems
  in file order; each suggestion kind; no suggestion beyond two edits; `<private>` for an unknown
  key under a sensitive group; a `config_version` mismatch reports one problem.
- Server: at most two blocks per start per platform; an admin is told once per server run, a
  non-admin never, nobody in singleplayer; nothing is said when the file loads; the VSS build
  names its own file and command.
- Client: `SETTINGS_BROKEN` in every connection state while the file is broken and never
  otherwise; the notice once per game start; the experimental-file line.
- Mutation checks on each rule.

## 2. "Share My Position: off" always reaches the server

### The gap

The preference frame is sent only after a session answer (`FarPlayerPreferenceDelivery.java:16-34`,
called from `ClientNetGlue.java:364`). A client that gets no answer sends nothing: Receive off or
nothing installed that can show terrain (no handshake, `ClientSessionGate.java:338-343`), a
server that stays silent (a version or ViaVersion mismatch), a dropped handshake (§0). A server
in the default mode shows that player. Players the server refuses are not affected: any answer
triggers the delivery.

The server side needs nothing. All four platforms register the preference channel
unconditionally and keep a frame from a connection that never handshook
(`FarPlayerBroadcastService.java:356-362`; read by the target filter at `:803-822`; cleared only
at disconnect). True since 0.14.0.

### The change (client only, no wire change)

**An opt-out is sent as soon as the server's preference channel exists, session or not.** The
delivery gets a second, weaker readiness: from join on it may send a frame whose `shareSelf` is
false. Everything else still waits for the session answer, as today. The check is made on the
frame at send time, so switching the option off during play sends it too.

Only the opt-out goes this way. With Share My Position on and no session, nothing is sent, as
today. Reason: on a server in `opt_in` mode a delivered "on" would show a player who is hidden
today, and who is visible is VoX's call (§8). A frame with `shareSelf=false` can only hide: it is
false in every mode, `required` ignores it for players without the hide permission, and the
frame's other fields do nothing without a subscription.

Details the reviews found:

- **Every join starts clean.** `sent` is reset at every join, not only by a handshake. On a proxy
  network the connection object survives a server switch (`FarPlayerClientSupport.java:36-39`), so
  without the reset the second server would never get the frame while the client says "sent".
- **A broken settings file sends the opt-out.** The inactive settings have sharing off
  (`LSSClientConfig.java:39-44`), and the file may well contain the player's "off". Hiding is the
  safe reading; the `SETTINGS_BROKEN` status says so (§1).
- **Switching back on without a session.** The server keeps the earlier "off" until the player
  reconnects, and the client cannot send "on" (above). The message after that save says so.
- **On a `required` server** these players now get the server's existing "this server requires
  position sharing" line. That is correct: they opted out and the server overrides it.
- Servers 0.11.0 to 0.13.1 accept the frame and ignore it without a session, and the client
  cannot tell. The README says so in one sentence.
- The player's own world and a LAN host are unchanged.

Messages after a settings save (en_us, zh_cn, zh_tw):

| State | Message |
| --- | --- |
| opt-out sent, no session | "Share My Position: off was sent to this server." |
| on, no session, an earlier "off" was sent on this connection | "Share My Position: on is saved. This server keeps your earlier "off" until you reconnect." |
| on, no session, nothing sent | the 0.22.0 text ("saved, but no server has received it yet…") |
| session | "Sharing preference sent to the server." (unchanged) |

**Operators can see it.** The `FarPlayers:` line of `/lsslod diag` gains `opted_out=<n>`: online
players whose kept preference is "off". It is also what the real-stack run reads (§5).

**Not changed on Paper.** The quit's `Remove` clears kept preferences before the newer-connection
guard (`PaperRequestProcessingService.java:1432`). The review traced the order: the `Remove` is
queued before the new connection exists and the lifecycle mailbox drains before runtime tasks, so
a rejoin's frame cannot be erased by the old quit. No change without a reachable case.

### Tests

`FarPlayerPreferenceDeliveryTest`: an opt-out with no session is sent once the channel exists and
retried while it does not; an opt-in with no session is never sent; switching off mid-connection
sends; a second join on the same connection object sends again; a session still sends everything.
`ClientSessionGateTest`: a join without consumers stays silent on the handshake channel.
`FarPlayerBroadcastServiceTest`: `opted_out` counts kept opt-outs. Each message in its state. Real
stack: `client-receives-nothing` (§5).

## 3. The client can say which "switched off" it is

### The gap

The client learns `enabled=false` and nothing else, so 0.22.0 says "switched off here: for
everyone, for this world, or for you" (`ClientVerdict.java:145`). The server knows which
(`ServerReceiverGlue.java:449-672`).

### The change

One reason in the session answer's flags. The flags field exists (`SESSION_FLAG_DENY_MAP_INGESTION
= 0x1`, `LSSConstants.java:369-377`), is sent only to clients that declared `CAPABILITY_MAP_POLICY`
(0.19 and newer), and every client from 0.19.0 to 0.22.0 tests bit 0 only
(`ClientSessionGate.java:572-575`), so new bits are invisible to them. No protocol version change.

**Exactly one reason, by precedence, and only with `enabled=false`:**

| Order | Bit | Meaning | Set when |
| --- | --- | --- | --- |
| 1 | `0x2` | off on this server | `!config.enabled()` (the setting, not "no service object") |
| 2 | `0x8` | needs a permission | the service gate denied this player (`deniedByServiceGate`, `ServerReceiverGlue.java:513-514`; Paper `LSSPaperPlugin.java:820`) **and** the operator allows saying so. When the operator does not allow it, **no reason bit at all** is sent. |
| 3 | `0x4` | off in this world | the session is registered and this world's distance is 0 |

One reason, never two: a player the gate denies is never registered and gets no later pushes
(`RequestProcessingService.java:1709-1745`), so telling them "off in this world" could never be
corrected when they walk to a world that serves others. With precedence they are told about the
permission, or nothing. With `enabled=true` every reason bit is zero, and the client ignores
reason bits on an enabled answer.

No reason bit means "not said": an older server, or an operator who keeps the reason private. The
client then shows the 0.22.0 sentence.

The reasons are computed by one function from the inputs that already decide `enabled`, at every
send (handshake, reload re-push, dimension change, revocation, grant replay). The server's memory
of the last map flag sent stays a Boolean (`ServiceGateState.java:91`): a reason only changes
together with `enabled`, which already pushes.

**The operator's switch.** The permission gate is also a quiet deny tool (0.22.0 plan §1), so
that one reason has a setting:

```yaml
service:
  require_permission: false
  # show_permission_refusal: true   # With require_permission on, a player without the permission
  #   is told "distant terrain here needs a permission you don't have". false = they see the general
  #   "switched off here". This is courtesy, not secrecy: a player can compare with a friend.
```

- The key is **commented out in the template**, with its default in code, so a file created by
  0.23.0 still loads on 0.22.0 (which rejects unknown keys). An older version ignoring it is
  harmless: it gates a capability older versions do not have.
- Changing it with `/lsslod reload` applies to refusals from then on; a player already refused
  keeps what they were told until they rejoin.
- "Off on this server" and "off in this world" have no switch: they are the same for everyone and
  already documented.
- **Proposed default: `true`. This is put to VoX before `0.23.0-beta.1`**, because the stable
  release is the beta's code. Without an answer the beta ships without the permission reason at
  all (the other two reasons do not depend on it).

**No server chat line.** The client has a notice with caps and a settle time; with the reason it
speaks precisely, in the player's language, and the server never speaks on the operator's behalf.

**Client.** `SERVER_OFF` splits; all four share the `server_off` notice counter:

| Verdict | Status text |
| --- | --- |
| `SERVER_OFF` (no reason) | the 0.22.0 text |
| `SERVER_OFF_EVERYONE` | "Not working: distant terrain is switched off on this server." |
| `SERVER_OFF_WORLD` | "Not working: distant terrain is switched off in this world on this server." |
| `SERVER_OFF_PERMISSION` | "Not working: distant terrain here needs a permission you don't have." |

Each has a notice of the same sentence ending "Nothing is wrong with your game." "Is switched off
on this server" is true when a broken settings file caused it; "has switched it off" would not be.

0.22 clients know none of these bits and keep their own "switched off here" notice.

### Tests

Wire: each bit round-trips; the 0.19-to-0.22 decoder reads bit 0 only from a frame with every bit
set (as `SessionConfigFlagsWireTest` does today). Both server cores, one table: for each cause and
each combination of causes, exactly the expected single bit; with `show_permission_refusal: false`
a denied player gets no reason bit in any world; no reason bit ever accompanies `enabled=true`.
Client: each verdict from each bit; reason bits ignored when enabled; the four share the cap. The
`forSession` census pin covers the new argument on both cores. Real stack: `off-in-world` (§5).

## 4. `/lss` works on the Voxy Server Side client

[Decision 0005](../decisions/0005-command-roots.md), client half. Players are the ones told to
type `/lss status` (README, issue replies, Modrinth), and 86 % of them run the VSS build.

The two builds stay byte-identical in their classes (`release_check.py:1461-1507`), so the extra
name is data: `lss-brand.properties` gains `alsoClientCommand=lss`, written only by the `vssJar`
tasks. The inline command trees in `LSSClientCommands` (Fabric) and `LSSNeoClientBootstrap` move
into one builder that takes the root name and is called once per name (built once per name,
never a Brigadier redirect).

**The extra name never hides a server command.** A client command wins over a server command of
the same name. The extra root therefore carries `requires(the server's command tree has no
"lss")`; a root that fails its requirement reads as unknown on the client and the command goes
to the server. The brand's own root behaves as today.

Help and messages keep printing the brand's own name. `check_brand_properties` accepts the new
key on VSS and refuses it on LSS.

Tests: `BrandTest`; the client command builder (both roots on VSS, one on LSS; the extra root
yields to a server command); the real-stack VSS run types `/lss status`.

## 6. Decided against

**Ignoring unknown settings** (the old "settings tolerance"). The approved idea was that a typo
should not switch the mod off. Review of the first design found that ignoring `far_player: {mode:
off}` turns far players on. This plan's research found the problem is general:

- Nearly every key in the server file is a switch or a limit the operator set on purpose: who is
  visible, who gets terrain, x-ray masking, generation, bandwidth, the size of the store. Ignoring
  a misspelt one runs the default, and the defaults are the open, larger values.
- "Fail closed instead" does not rescue it. Forcing `privacy.xray.mode: on` drops every stored
  row of the dimension, twice (`SqliteLodStore.java:2687-2704`). Forcing
  `request_no_map_ingestion: true` cuts off every client older than 0.19.0.
- Running the last file that loaded was considered and rejected: an edit that tightens a setting
  would silently not apply.

What strictness buys is consent: the mod never runs a configuration the operator did not write.
So the file stays strict, the one certain case is accepted (boolean spellings), and a mistake
becomes impossible to miss (§1). Decision 0009 records this.

**The VSS server commands answering to `/lsslod`, and `lss.admin`.** The server half of decision
0005 costs a Paper `plugin.yml` rewrite, a loosened brand check in `release_check.py` (twice:
1.21.1 carries its own copy), and Sponge wiring, and it has a hole: `permission:
vss.admin;lss.admin` leaves `lss.admin` undeclared on the VSS build, Bukkit gives an undeclared
node to operators, and an operator whose `vss.admin` was taken away would get the command back.
Operators read a console and can translate a name; the admin chat line (§1) and the help print
the build's own. Decision 0005 is amended: the client half is built, the server half is not,
until operators are found typing the wrong one.

**The server answering a protocol version it does not speak.** A 0.23 server speaks 20, and every
client since 0.10.0 (2026-08-08) announces 20 first. The silent branch is reached only by 0.4 to
0.9 clients whose compatibility rung the operator turned off, and by nothing newer; an answer
would not help them (their version is refused on purpose), and 0.2 and 0.3 clients would be kicked
by it. When a protocol 21 exists, the client's ladder already handles it.

**A server chat line for refused players.** Replaced by §3.

**"Voxy is installed but not drawing"** read "Working", which is the worst answer this theme can
give. The look found a reliable signal, so it is a verdict in this release (§6a).

## 6a. Voxy says when it is not drawing (built)

What Voxy exposes, read from its source on the 26.3, 26.2, 26.1, 1.21.11 and 1.21.10 branches,
its development branch and the NeoForge fork (a Voxy without this surface gives no answer, and
no answer changes no verdict):

- `VoxyCommon.isAvailable()`: false when Voxy switched itself off at startup because the
  graphics card or driver lacks what it needs (compute shaders, indirect parameters) or has the
  AMD depth-sampler defect. It logs "Voxy is unsupported on your system." and creates no
  instance for the whole game.
- `VoxyConfig.CONFIG.isRenderingEnabled()`: false when the player switched Voxy, or its
  rendering, off in Voxy's settings.
- On 26.3 Voxy refuses the Vulkan backend when the game creates its device, so the game falls
  back to OpenGL. A Voxy on Vulkan is therefore not a case.

The status asks both (`VoxyCompat.drawState`) and answers `RENDERER_UNSUPPORTED` or
`RENDERER_OFF` where everything else is in order: a cause on the server or the player's own
receive switch is always named first. "Cannot run on this computer" is said once in chat under
the nothing-to-show cap; the player's own switch is never announced. The Distant Horizons source
asks too (it would otherwise read "waiting" for ever).

One trap, pinned by a test: Voxy's config class decides at class load, from the same
availability answer, whether to read the player's file or hand out a switched-off stand-in.
The probe touches that class only after Voxy has said it is available.

Not changed, noted for a later release: a client whose Voxy has no instance still asks for
terrain. Each column is refused by Voxy and re-requested up to the failure cap before it parks
(read from the code, not measured). Not registering the Voxy consumer in that state would stop
the wasted download; it changes when a client starts a session, so it wants its own plan.

Also from the 0.22.0 visual pass: the status details show "unknown" instead of `ingest=-1`, and
the option label "Extend Far Player Draw Range", which Sodium cut off, is now "Extend Draw
Range" (the two Chinese labels were short enough and are unchanged).

## 9. Review fold (2026-11-13)

Two reviewers read the draft against the code: one for failure cases, one for the decisions. No
blockers. What changed:

| Finding | Disposition |
| --- | --- |
| An opt-out switched on during play was never sent; on a proxy only the first server got it | the check moved to send time, and every join resets `sent` (§2) |
| "Will send no handshake" is a prediction and misses silent servers and dropped sends | the opt-out is sent whenever the channel exists (§2) |

## 12. The client's disconnect cleanup runs on the client thread (2026-11-13)

Found by following §11's crash to the other side. One reader audited the client's disconnect
body thread by thread; every finding below was checked against the code.

### The gap

On Fabric the client's cleanup hung on `ClientPlayConnectionEvents.DISCONNECT`. Fabric fires
that event from whichever comes first, netty's `channelInactive` or the client thread's own
disconnect handling, and netty wins on every kick and server stop, and usually when the player
presses Disconnect. So the cleanup nearly always ran on a network thread, while the client
thread was still ticking and drawing with the same state. The code was written for the client
thread (its comments say "render thread" and "main-thread reset"). What could go wrong:

| What the network thread did | What the client thread was doing | What a player could get |
| --- | --- | --- |
| Tore down the request manager: cancelled deliveries, cleared the tracker, copied and cleared the column map | The manager's tick (prune, scan, track) or a column handler, on the same unsynchronized maps | A crash to desktop in place of the disconnect screen; or an exception on netty, which the game swallows on a closed channel, so the rest of the cleanup never ran: no cache save, the next server starts with the old server's far players; or a column stamped "received" that no consumer saw, a hole until a re-download |
| Cleared the far-player proxies and reset the renderer's crash latch | The render pass, reading the same maps | The pass threw, was contained, and latched "off" after the reset: far players invisible for the whole next session |
| Copied and cleared the Distant Horizons session's maps | The same session's tick | An exception on either side, as above |
| Wrote "no notice shown yet" | The notice book's tick wrote "shown" | The next server's notice suppressed |

All rare: each needs the two threads inside the same structure within milliseconds. None has
an issue. NeoForge is not affected: its logged-out event is posted from `Minecraft.disconnect`,
on the client thread (one caller on 1.21.1 and on 26.3, read from the classes).

### The change

The Fabric client stops listening to that event. A client mixin, `ClientDisconnectHook`, runs
the cleanup at the head of `Minecraft.disconnect`:

- That method is where every way out of a server ends: the server closed the connection (the
  client thread notices on its next tick and disconnects), the player left, the game is
  quitting, a kick while a proxy was moving the player. The overloads funnel into one, which is
  the hooked one (`(Screen, boolean, boolean)` on 26.x and 1.21.11, `(Screen, boolean)` on
  1.21.1).
- It runs on the client thread, before the level is cleared, so the decode worker stops before
  Voxy and the maps are torn down. NeoForge posts its logged-out event from the same method, for
  every call: the two loaders now behave alike. Like that event, the hook also fires when there
  is no session, and the cleanup is a no-op then.
- A failure in the cleanup is logged and contained; the player still gets out, and the next
  join's defensive teardown covers the rest. (On netty it was swallowed without a line.)
- The cleanup logs an error if it ever runs off the client thread.

After a server-side close the session now stays up until the client thread notices, at most one
tick, as on NeoForge. Requests sent in that tick go into a closed connection and are dropped;
nothing throws, and no notice or status changes (read through by the first reviewer).

### Rejected

- **Hand the cleanup to the client thread's task queue**, as §11 does on the server. The game's
  disconnect begins by dropping every queued task, and a quit never drains the queue again: the
  cleanup, cache save included, would often not run at all.
- **A flag that the next client tick settles.** It runs, but after the level is gone: the decode
  worker keeps delivering to Voxy for up to a tick after Voxy closed its world. On the Disconnect
  button, the most common path, that would be the rule, not the exception.
- **A lock around the cleanup and everything it races.** Every tick, frame, handler and command
  entry would have to take it; one missed entry point brings the race back.
- **Splitting the cleanup** into a thread-safe half for netty and the rest for the client
  thread. The order inside it is load-bearing (report undelivered columns, then tear down, then
  save; the map sessions after the manager), and each split found so far makes a hole.

### Not changed

- A server-initiated reconfiguration (a proxy moving the player between servers) runs no cleanup
  on either loader, as before: the next join's defensive teardown covers the manager. A kick
  during that move now does run it (below).
- The server side of a LAN host is §11.
