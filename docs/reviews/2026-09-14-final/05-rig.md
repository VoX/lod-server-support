## Findings

### R05-1 — medium — a signal-initiated stop gives the runner 3 s before SIGKILL, so the graceful protocol, the journal's terminal write and the cleanup receipt are lost

Location: `scripts/lib/owned-process.py:94-131` (escalation at :102 `SIGKILL if elapsed >= 3`, `os.killpg` at :105, no `--rig-run-root`-specific grace) versus the runner's own bounded shutdown in `tools/rig/rig.py:506-646` (`stop_stdin` + `proc.wait(timeout=20)` :508-514, `terminate_owned` 5 s per process :346-359, post-cleanup checkers :522-618, manifest write :645, `terminal()` :646).

Trigger: SIGTERM/SIGINT/SIGHUP reaching the `tools/rig/rig run` wrapper (operator Ctrl-C, `kill`, terminal hangup) while any owned participant needs more than ~3 s to exit — a Minecraft server saving its world, a JVM running shutdown hooks, Prism, or a fixture. `rig.py` handles the signal correctly (sets `stopped`, leaves the observe loop, enters `finally`), but the outer supervisor SIGKILLs the whole owned session — `rig.py` included — at 3 s.

Consequence (observed, control B): `launch-journal.json` stays `terminal: false`, `manifest.json` stays `running`, `supervisor-cleanup.json` is never written (`[harness] Rig cleanup receipt unavailable: nonterminal launch journal`), the wrapper exits 143 after 3.12 s. Collection then fails closed (`owned process evidence invalid: nonterminal launch journal`, cleanup `incomplete`) — correct — but the attempt is permanently uncollectable: `experiment.record_failure` requires `evidence/result.json` with `cleanup: complete` and clean ownership (`experiment.py:71-84`), so a measured/calibration slot interrupted this way can neither be recorded as a failed slot nor reclaimed by a new run (`run_claim.acquire` → `selected intent already claimed by another run`, `run_claim.py:40-41`), i.e. the preregistered experiment is wedged by an operator interrupt. The plan (§8) requires "graceful shutdown followed by bounded owned-descendant termination" and "persist recovery information after runner failure"; the documented graceful path (`rig stop` → `stop` marker, `rig.py:667-670`) is unaffected, but the signal path is the one an interactive operator actually hits. The interrupted disposable world save is also cut short (harmless for evidence, since the run cannot pass).

Observed vs hypothesis: observed. Control B: created a run whose only launch is a Python fixture that ignores SIGTERM and sleeps; started `tools/rig/rig run <run>` in its own session; sent SIGTERM to the wrapper once `processes.json` listed the fixture. Result: `wrapper_exit: 143`, `seconds_until_wrapper_exit: 3.12`, `journal_terminal: false`, `manifest_status: running`, `supervisor_receipt_exists: false`, `fixture_pid_gone: true`, `collect_exit: 1`. Ownership itself held (nothing survived).

Verification / fix: in `owned-process.py`, when `--rig-run-root` is present, (a) on the first stop signal touch `<run>/stop` and let the runner drain (this is exactly the runner's designed stop path), and (b) extend the TERM→KILL grace to cover the runner's bounded protocol (≥ 20 s stdin stop + 5 s per-process terminate + checker time; e.g. 60 s), keeping the hard bound. Add a `test_runner.py` case: fixture ignoring SIGTERM for 5 s; after SIGTERM to the wrapper assert `launch-journal.json.terminal == true`, `manifest.status == 'failed'`, `supervisor-cleanup.json` present and `collect` cleanup `complete`.

### R05-2 — low — `private_display()` accepts a display whose owned Xvfb already exited when a foreign X server answers the readiness probe

Location: `tools/rig/rig.py:262-279`. The readiness loop (`:272-275`) runs `xprop -root` first and checks `proc.poll()` only inside the loop body; a first-iteration `xprop` success skips the liveness check entirely. `spawned()` (`:269`) then records the dead child (a not-yet-reaped zombie still yields a valid `/proc/<pid>/stat` creation identity — control C confirmed `alive()` reports `True` for a zombie), `display.json` is written, and `env.DISPLAY/XAUTHORITY` are set for every subsequent launch. `verify_private_xvfb` (`:292-300`) is never called from `private_display`.

Trigger: an X server already active on the randomly chosen display number (`:100`…`:65635`, `:255`) that accepts a connection presented with the run's cookie file — i.e. a same-user or access-control-disabled server. Xvfb then fails with "Server is already active for display N" while `xprop -root` succeeds against the foreign server.

Consequence: the GPU probe (`glxinfo`, `:416-419`/`:427-430`) and every participant launch (server, Prism/client) run with `DISPLAY` pointing at the foreign server for the whole readiness phase (up to the 180 s server marker plus client `ready_conditions`). No input or capture can reach that display: `guard_display` → `verify_private_xvfb` resolves the zombie's `/proc/<pid>/exe`, which fails (`FileNotFoundError`, control C), so every `XInput`/`native_window.find` path fails closed; and the observe loop's child-exit check (`:491-492`) fails the run as soon as readiness completes. So there is no false pass — the gap is that a game window can be created on a foreign display before the run fails. Not a maintained-recipe trigger; it needs a display-number collision.

Observed vs hypothesis: observed offline (control A): with `rig.subprocess.Popen` replaced by `/bin/true` (Xvfb exiting at once) and `rig.subprocess.run` returning rc 0 for `xauth`/`xprop`, `private_display()` returned `:58104`, the owned child's returncode was `0`, `display.json` was written, the journal entry was `spawned`, and `env.DISPLAY` was `:58104`. The real-X trigger was not exercised (no X server launched).

Verification / fix: after the readiness loop add `if proc.poll() is not None: raise ValueError('private display exited during startup')`, and call `verify_private_xvfb(root, {'display': display, 'xvfb': display_owner})` before returning (it already pins the executable, `-nolisten tcp`, `-auth <run>/Xauthority`, and the 0600 mode). Alternatively spawn Xvfb with `-displayfd` and read the allocated number instead of guessing. Control A then raises. Add the mocked case to `test_private_display_context.py`.

### R05-3 — low — launch environments are inherited wholesale, not built from an allowlist

Location: `tools/rig/rig.py:400-401` (`env = os.environ.copy()`), `:276-277` (host `WAYLAND_DISPLAY` popped and `DISPLAY`/`XAUTHORITY` replaced only inside `private_display`), `:447` (`Popen(..., env=env)`); `run_server_smoke.py:18` and `launch_prism.py:81` pass that environment on to the nested JVM/Prism children.

Trigger: any `rig run`. Observed (control E, `linux-headless` fixture launch without `private_display`): the owned launch saw `DISPLAY=:0`, `WAYLAND_DISPLAY=wayland-0`, `LSS_HARNESS_LOCK_FD=10` (the descriptor itself is correctly not passed — `close_fds=True` — but the variable is), and an injected `R05_SYNTHETIC_SECRET` from the operator's shell.

Consequence: (1) on a `linux-headless` runtime without `private_display`, a GUI participant would open on the ordinary WSLg desktop `:0`; the runner rejects the desktop only for input/capture (`guard_display`, `:302-316`) and via `require_gpu` (`:431-432`), not for the launch itself. Every maintained composer that carries a GUI client sets `private_display: true` or uses `isolated-linux-prism` (`assemble_platform_recipe.py:39`, `prepare_folia.py:25`, `prepare_prism.py:66`); the two composers that set `private_display: false` (`prepare_source_seed.py:18`, `prepare_prefill.py:21`) strip every non-server launch first — so no maintained recipe hits this, but the invariant is not enforced by the runner. (2) Operator shell variables — this project's local notes document `set -a; source ~/.bot.env` shells carrying `MODRINTH_PAT`, `RCON_PASSWORD`, `ARCHON_TOKEN` — reach the game/server/Prism processes and every fixture. Private logs and the export record do not carry the environment (`export_validation.py` indexes hashes only), so no exported-evidence leak was found; this is a containment hygiene gap against the plan's "strip inherited … environment bindings" wording (§8) and "credentials never enter … command lines" (§16).

Verification / fix: build the child environment from an allowlist (`PATH`, `HOME`, `LANG`/`LC_*`, `TMPDIR`, `XDG_RUNTIME_DIR`, the private `DISPLAY`/`XAUTHORITY`, `ALSOFT_DRIVERS`, `LSS_RIG_RUN_ID`, the vetted `gpu_environment` keys, plus the launch's declared `env`), unset `DISPLAY`/`XAUTHORITY`/`WAYLAND_DISPLAY` whenever no private display was created, and refuse a launch whose argv is a known GUI client (`KnotClient`, `--quickPlayMultiplayer`, `launch_prism.py`) when the runtime has no private display. Regression: control E's fixture must observe none of those keys.

### R05-4 — low (pre-existing baseline code; hypothesis) — `os.killpg` by a reaped PID in the ownership supervisor

Location: `scripts/lib/owned-process.py:81` (`result = proc.poll()` reaps the direct child), `:93` (`orphaned` branch entered after the child is gone), `:102-108` (`os.killpg(proc.pid, sig)` on each escalation, i.e. TERM immediately and KILL ≥ 3 s later). Present unchanged at baseline (`48268c7d:scripts/lib/owned-process.py:85-88`).

Trigger: the group id (= the reaped child's PID) becomes free once no member of that process group remains, and the kernel may then hand the number to an unrelated new session/group leader before the next `killpg` (the KILL escalation is issued up to 3 s after the TERM). Requires PID wrap-around within that window (`pid_max` = 4194304 on this host), so the probability is very low; not observed.

Consequence: a PID-only signal to a foreign process group, contradicting "PID … alone never authorize[s] termination" (plan §15 R5). The per-PID loop (`:109-115`) is safe (it re-reads the supervisor's current adopted children each iteration).

Verification / fix: issue `killpg` only while the group is known non-empty (e.g. scan `/proc/*/stat` for members with `pgrp == proc.pid` and a start time ≥ the child's, or skip the escalation `killpg` when the direct child is already reaped and rely on the adopted-children loop, which already covers escaped children via the subreaper). A unit test can pin "no `killpg` after the direct child is reaped" with a fake `os.killpg`.

### R05-5 — low — `metric-schema.json` is descriptive only: nothing reads it and it is outside every identity binding

Location: `tools/rig/metric-schema.json`; no reader anywhere in `tools/` (grep: only `required-matrix.json` is read by a tool); `tools/rig/toolchain.py:12` snapshots only `.py/.java/.sh`, so the file is not part of `runtime_tools`; the thresholds it states (1000 samples, 0.95 RSS fraction, p50/p95/p99) are hard-coded independently in `performance.py:118-120` and `metrics.py:26`.

Consequence: `docs/operations/disposable-rigs.md` calls it "the frozen metric schema", but freezing it has no effect on assembled reports, and editing it is invisible to tool-identity verification (`toolchain.verify`) and to the scoped checker closure (`scenario_checker_identity.closure`, which follows Python imports only). The enforced schema is whatever `assemble_metrics.py`/`performance.py` emit and require. No incorrect measurement acceptance follows from this; it is an identity/documentation binding gap.

Verification / fix: either have `assemble_metrics`/`performance` load the thresholds and metric names from the JSON and validate report keys against it, and include `metric-schema.json` (and `required-matrix.json`) in `toolchain.snapshot`; or reword the document to say the JSON is a description of the code-defined schema.
