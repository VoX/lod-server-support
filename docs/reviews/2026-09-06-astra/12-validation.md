## Confirmed findings

### P2 — Soak's occupied-port refusal occurs after it deletes the running fixture

**File:** `scripts/soak.sh:425` versus `:598`. Additional mutations: client cache removal at `:482`/`:501`/`:507`, staged configuration at `:515`, and current logs/results removal at `:594–595`.

**Trigger:** A previous/stale soak server still owns this checkout's configured soak run directory and port 25565. Start another ordinary `./scripts/soak.sh fresh-backfill` (or another accepted scenario) from the same checkout. The script builds, stages the world, clears cache, overwrites configuration, and deletes current logs/results before its intended pre-flight check discovers the listening server and exits. A second invocation concurrent with an active soak has the same shape. There is no lock protecting staging.

**Impact:** The rejected invocation has already removed the live fixture's world directory and current evidence. Existing open files can continue operating against unlinked storage while subsequent saves recreate an inconsistent directory tree. The active run's world/evidence is no longer a valid reproducible fixture; its client cache may also have been removed mid-use. The refusal message incorrectly suggests nothing started, although destructive shared-state work already ran.

**Evidence:** Direct control flow; the occupied-port function is defined at `:363`, but called only after staging at `:598`. Parent independently confirmed this ordering. This concerns a prior soak using the **same scratch paths**. The user's currently running regular test server in a different directory on port 25564 is not implicated, and was neither inspected operationally nor changed. Parent also found the same ordering on the other reviewed lines; keep one cross-line harness fix.

**Proposed fix:** Acquire ownership of the relevant run directories and shared port/client resources before build or staging, then check port availability before any mutable pre-flight action. Keep a check immediately before launch as a useful external-process race detector, but an early check alone does not serialize two concurrent orchestrators. Carefully design `all` and automatic fresh-backfill recursion: the outer owner must retain a single lock through child phases without deadlocking on its own inherited lock. Cross-worktree calls share port 25565 even when directory paths differ, so an exclusively per-checkout lock is insufficient for the shared-port claim. Ordinary non-harness listeners must cause an untouched-fixture refusal.

**Regression:** A safe copied-script fixture with stubbed build/process/port dependencies should plant sentinel world/cache/log/result files, simulate an occupied port, and assert refusal leaves every sentinel and configuration byte intact and invokes no build/start hook. A separate two-orchestrator fixture should hold the first invocation before staging and prove the second cannot mutate shared scratch space. Test `all` and auto-prime reentrancy. Do not run this regression against the real script's live paths.

### P2 — Standalone benchmark can return success while showing a previous run's results

**File:** `scripts/benchmark.sh:176` clears only producer run-directory files; `:213–220` logs but swallows a failed server wait; `:229–242` warns on absent new JSON without removing destination artifacts; `:283–289` prints “Benchmark Complete” and whichever `benchmark-results/server.json` exists.

**Trigger:** Run the documented direct benchmark CLI once successfully. Run it again, and let its server become ready but then crash, or exceed the benchmark deadline, before final metrics export. The old `benchmark-results/server.json`, `client.json`, and JFR destination files remain because setup uses `mkdir -p` and per-cycle cleanup removes only the run-directory producers. Missing new exports only produce warnings. The command returns zero and prints the old server JSON beneath the new completion message. A missing client export can similarly leave a previous client result paired with the current server result.

**Impact:** A direct caller or human comparing the shared output directory can attribute previous-run metrics to a failed new configuration, or analyze a mixed server/client/JFR set. This is a reproducibility/false-success defect, not a claim that all higher-level performance gates are bypassed.

**Evidence and scope:** Source-confirmed, no runtime probe needed. `scripts/benchmark_compare.sh:139` and `scripts/store_gate.sh:81` already delete destination artifacts in their own wrappers; those protected paths are excluded from this finding. The protection should belong in the publicly documented underlying `benchmark.sh` command too. Its fixed `RESULTS_DIR` is initialized at `:37`, and the final `if` with no matching file still completes successfully in Bash.

**Proposed fix:** At the start of each cycle, retire that cycle's destination JSON/JFR artifacts as well as producer artifacts, or write to a fresh run-identified output directory and publish a complete manifest only after success. Fail the cycle on an unexpected server/client termination or missing required fresh JSON. Preserve optional client-JFR behavior: clients intentionally use `halt(0)` and may not finish JFR. A fresh-world run must not overwrite the reusable base with an incomplete failed fixture. Preserve both populate/measure artifacts for warm-join and verify each belongs to its own successful cycle.

**Regression:** A fully isolated shell fixture with simulated successful initial artifacts, followed by a “ready then failed without export” run, must return nonzero and expose no stale current-run JSON. Add a partial-export arm (new server, no new client) and a warm-join populate failure that prevents measure/base promotion. Assert optional missing client JFR remains allowed. Use stub process helpers and temporary paths; no Minecraft launch is needed.

## Validation coverage and accepted limits

- **Entrypoints:** `GameTestEntrypointContractTest` recursively compares source classes carrying `@GameTest` to the exact Fabric server entrypoint set and pins absent client entrypoints on this line. Its source/metadata inputs are registered on the Gradle test task, so a metadata-only change invalidates the task. Eight current server classes are listed. A future annotation/generator mechanism outside this scanner would need a deliberate coverage update; no presently unregistered class was found.
- **NeoForge zero-test defense:** Build CI now requires a required-test summary after `runGameTestServer`, uses this line's `neoforge.enabledGameTestNamespaces=lsstest`, and includes common sources in the mod layer. The loose regex can syntactically match zero, but a zero-function run is **not** established as a reachable green: local MC1.21.1 mapped `GameTestServer.create` bytecode rejects an empty test collection before starting. Artifact `/tmp/lss-review12-gametestserver.txt` records that bytecode. No zero-test finding is promoted.
- **Retries/known flakes:** CI retries gametests once, emits warning annotations, and preserves first-attempt logs/crash reports. Tier 1 is not retried. Existing wall-time waits in the TwoPlayer tests close the documented tick-vs-wall duplicate-grace and disk-IO timeout races. Do not reclassify a logic assertion as the old polling-timeout flake, and do not claim Tier 3 validation on this line.
- **Behavioral versus source tests:** Source and bytecode contracts protect registration, line API shapes, and wiring; pure behavioral tests protect state transitions. They do not prove a real loader applied every mixin or every external jar supplied the expected runtime class. This is a stated evidence boundary, not a reason to add tests duplicating implementation text. The existing actual golden-jar checks and the actual Xaero jar inspection in report06 are materially stronger for those external surfaces.
- **Soak false-green guards:** `run_checker` requires server snapshots, every expected client run, server timeline-complete and client disconnect evidence, known schemas, verified quiescence, non-vacuous client-law window floors, and a traffic-bearing conservation window except intentional enabled-false. The quiescent endpoint correction uses bounded at-or-before client rows. A6 counters and A7 anomaly coverage include pre/post-quiescent tails. No concrete new false-green law defect was established in this pass.
- **Checker tolerance:** Malformed JSONL lines warn and are skipped; unknown additive fields are reported once. This does not authorize dropping required completion/schema/coverage evidence: those gates still fail when their evidence is absent. Counter sample boundaries and dimension transitions intentionally do not promise per-row atomic conservation. Whole-box isolation and wall-time budget assumptions remain relevant when interpreting timing failures.
- **Diagnostic semantics:** Exporter contract tests pin key/type parity across Fabric/Paper plus high-water sampling and reset semantics. `mspt_avg_window` is explicitly **wall time divided by sampled ticks**, including ordinary pacing; it is a cadence/TPS measure, not server tick execution CPU time. Do not use a stable approximately 50 ms value to assert that sub-budget main-thread work did not grow. The sampled CPU/JFR gates are the stronger evidence for CPU regression. No change to this intentionally pinned gauge is proposed here.
- **Trace tooling:** The bounded asynchronous writer has explicit drop/cap accounting, rotation, exception containment, and bounded shutdown. The trace validator checks row schema/order, not whether useful gameplay was captured; an empty schema-valid file is therefore insufficient evidence of a collection. The operation plan separately requires ACTIVE log evidence, a valid bridge rung, and visible post-flight rows. No additional empty-file product defect is claimed.
