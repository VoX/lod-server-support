## Confirmed: P2 — the live master switch does not control the acquisition session

**Primary location:** `xplat/src/main/java/dev/vox/lss/networking/client/ClientNetGlue.java:454` (manager ticks whenever serverEnabled, independently of `receiveServerLods`). Additional implementation: `LodRequestManager.java:346`/`:385`, `ClientColumnProcessor.java:156`, `ClientSessionGate.java:196`; UI wiring `config/menu/ClientOptionCatalog.java:63`, `config/menu/SaveHook.java:24`. User promise: `fabric/src/main/resources/assets/lss/lang/en_us.json:4`: “Turn off to stop all LOD downloads.”

**Trigger/state transition:** Start an enabled remote session while filling terrain; change Receive Server LODs to OFF in either supported Sodium page and apply. The catalog binding immediately mutates the live CONFIG and the SAVE hook only persists it. There is no session teardown, explicit empty want-set, or acquire-loop guard. The manager continues to declare missing columns at its normal cadence. Every resulting VoxelColumn is first stamped as received, then `ClientColumnProcessor.scheduleProcessing` sees OFF and drains it through `reportAndClearBacklog`, which reports an ingest failure. The manager forgets the stamp and requests the same column again. The fourth such delivery exceeds `MAX_INGEST_FAILURES == 3` and parks the position as session-satisfied. Turning ON again does not clear that park; those undelivered positions are skipped until dirty invalidation, range prune/revisit, reset, or a new session.

**Impact:** OFF continues consuming bandwidth and server read/generation resources. It can traverse the entire acquisition disc while serving/discarding and exhausting each position's retries. ON then leaves holes despite a healthy consumer. Complementary trigger, same missing lifecycle: join with OFF, then apply ON. JOIN skipped the handshake and left the discovery ladder disarmed; applying ON has no handshake trigger, so the session stays inactive until reconnect or another external establishment event. The only other handshake entry, `triggerHostHandshake`, is wired to LAN opening, not this option.

**Evidence / test gap:** Production `onEndClientTick` calls the manager before processor scheduling, and neither `LodRequestManager.tick` nor `tickWithContext` examines the master switch. `ClientColumnProcessorTest.receiveServerLodsDisableFlipReportsClearedBacklog` (CL-044) asserts that already-received backlog is honestly unstamped; it does not drive subsequent acquisition or OFF→ON. `ClientSessionGateTest` pins suppression at JOIN, but not enabling mid-connection. Menu tests assert field persistence, not session transitions. External probes assert (1) no nonempty declarations after OFF and (2) no permanent park on ON after four OFF-discard deliveries. They use the existing manager tick/receive/processor seams, avoid server/IO/executor work, and are expected to fail on the reviewed code. Parent will record execution results.

**False-positive discipline:** The processor comment explicitly acknowledges and bounds a “clear-while-still-serving loop,” and CL-044 deliberately requires honest reports. This finding does not propose dropping those reports or undoing the retry cap. That containment is correct for genuine failures and late arrivals; it does not satisfy the master toggle's acquisition semantics. The missing switch-to-session transition is the defect.

**Proposed fix:** Give the master option a dedicated apply/session transition (or detect its edge in client glue). OFF must issue an explicit empty want-set, stop new acquisition, and retire/report queued data without repeatedly consuming failure retries on newly requested work. Preserve truthful stamps and governor/link state as appropriate, with old-worker epoch protection. ON must establish/rebuild a manager and re-announce when no session was established, including the OFF-at-JOIN case. Do not simply add `if (!receiveServerLods) return` around manager.tick: without the empty declaration the server may finish its old backlog, and without ON establishment the second trigger remains broken. A session retirement/rebuild shared with existing service-gate handling is preferable to special-case un-parking masks.

**Regression plan:** Both loader-independent manager/processor paths; both directions; exactly one OFF empty declaration; no nonempty requests while OFF; late arrivals remain truthfully unstamped; ON resumes and requests lost data without artificial capped parks; OFF-at-JOIN→ON announces once; duplicate Apply stays idempotent. Keep CL-044 and the existing cap/sibling-report pins unchanged. UI catalog test should pin the new save hook on the master option. Run existing ClientSessionGateTest, ClientColumnProcessorTest, LodRequestManagerTickTest and catalog/menu suites after implementation; live client toggle check on one supported loader is the final wiring check.
