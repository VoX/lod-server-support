## Required design corrections

1. **WI-13 must own actual process lifetime, not only the Gradle launcher.** `scripts/lib/mc-run.sh` currently sets `SERVER_PID`/`CLIENT_PID` from the background `./gradlew` process and cleanup kills/waits only that PID. An implementation must not assume that inheriting a flock descriptor into that launcher makes a daemon-spawned game process hold the lock, or that launcher termination proves the game process has stopped. Specify an owned launch/process-group or explicit child identity strategy, terminate and reap owned descendants before releasing shared-resource ownership, and keep unrelated listeners untouched. Conversely, do not accidentally let persistent Gradle infrastructure retain a lock after the game exits. Add an isolated fixture with a launcher that exits/leaves a child and a persistent daemon model, plus abnormal parent exit. The intended bound is actual scratch-world use, not arbitrary ancestry or all JVMs matching a command line.

2. **WI-10 should promise malformed-parse atomicity only.** `RuntimeSettings.applyAndPersist` currently invokes `key.apply()` before `config.validate()` (`RuntimeSettings.java:222–226`). The plan's phrase “Validation/parse failure still means no runtime mutation” promises stronger rollback than the current API. Keep the documented malformed-value guarantee and do not expand this feedback task into whole-config transactional validation. The accepted correction is to narrow that sentence; no new rollback mechanism. Preserve Fabric's integer success result for a live apply even if persistence fails, and Paper's command-dispatch success semantics; persistence outcome belongs in explicit user feedback and the returned operation result. Test that the distance re-push still occurs on persistence failure.

3. **Run full wrappers for chained acceptance scenarios.** The scenario table's `store-offline-verify` and `store-migration-join` names are phases, not sufficient standalone gates. Use `SOAK_PLATFORM=fabric|paper ./scripts/store_offline_edit.sh` as supported, and `SOAK_PLATFORM=fabric ./scripts/store_migration_gate.sh` for the Fabric-only migration chain. The former verifies cross-phase edited/control hashes; the latter creates the legacy fixture and proves downgrade/held-walk/client-join/resume ordering. Directly invoking the named second/third phase can miss fixture ancestry or wrapper-only checks. Similarly use `summary_evicted.sh` and `stamp_heal.sh` if those chained gates are selected. Wrapper ownership must cover config staging, carry-world copies, result discovery and assertions between child runs.

4. **Make the new actual-script regression suite a named repeatable gate.** WI-13 requires executable fixtures, but Layer 4 currently lists only syntax checks and existing checker selftests. Add the eventual command for the new suite to that layer and the appropriate CI script-selftest step. Otherwise future shell edits can pass CI without exercising the ownership/provenance protections. Include all changed helper/wrapper scripts in syntax checks, not only `soak.sh` and `benchmark.sh`.

## WI-13 implementation constraints confirmed

- Acquire ownership before **wrapper-side** mutation as well as before child staging. Known participating wrappers include `store_gate.sh`, `benchmark_compare.sh`, `store_offline_edit.sh`, `store_migration_gate.sh`, `summary_evicted.sh`, and `stamp_heal.sh`; inspect other launch wrappers before claiming the resource graph is complete.
- A stable per-user lock outside disposable trees, inherited by verified descriptor identity, is sound. A plain environment opt-out is not. Reentrant children must prove the descriptor refers to the expected resource and shares actual locked ownership; an unrelated descriptor with the same number is insufficient. Do not unlink lock files.
- Since supported harnesses contend for the same listener port, a simple coarse shared ownership gate may be preferable to several partially inherited locks if it satisfies all current workloads. If using multiple resource keys, canonicalize paths and enforce one acquisition order even across auto-prime and wrappers, with no later lock-order inversion. Port ownership alone does not prove that unrelated existing scratch-directory users are safe to overwrite.
- Failed current cycles must not leave stale shared aliases labelled as current. Retaining prior successful artifacts under unique run IDs is appropriate. A run manifest must identify which populate/measure cycle generated each required JSON and which optional JFR is absent.
- Capture exit status before cleanup overwrites it. Existing benchmark clients intentionally export on disconnect and `halt(0)`; this is successful completion. Missing required JSON, malformed JSON, timeout or unexpected nonzero process status must fail, while missing optional client JFR must not. Preserve useful partial logs.
- Publish a fresh base only after successful completion. Failed warm population must prevent measurement; failed measurement must not publish a successful current-run alias. Keep `BENCHMARK_CONFIG_STAGED=1` behavior and wrapper workload/config identity.
- Actual-script fixtures should use temporary copies/path seams and fake launch dependencies, and fail closed if a real launcher is reached. Assert sentinel contents and mtimes, losing-invocation nonmutation, recursion, cross-worktree contention, abnormal cleanup and post-cleanup lock reuse. Never point a fixture at real run dirs or an installed Prism instance.

## WI-10 and WI-14 assessment

The nonthrowing `trySave`-style outcome plus compatibility `void save()` wrapper fits current callers. Keep adopted `activeFileName`, atomic-move fallback, hidden-key serialization and original logging. A directory obstruction at the sibling `.tmp` path is a reliable root-safe failure fixture; permission-bit tests would not be. Avoid exposing raw exceptions in command output or treating a successful runtime mutation as rolled back.

WI-14's two explicit 1.21.11 C2ME configurations match source: regular-map alpha.0.18 (`MfQIu1Y0`) and benchmark alpha.0.26 (`879vA5z6`). Document/test both before consolidation; neither mismatch proves incompatibility. Profile inventory should distinguish internal loader/MC metadata from filenames and actual launch evidence, preserve disabled mods and user-purpose profiles, and use isolated clones for destructive/error injection. No automatic profile replacement or C2ME upgrade is warranted.
