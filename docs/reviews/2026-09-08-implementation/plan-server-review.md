## WI-2 — implementation requirements

1. **Guard queued ticket admission, not just ready-result consumption.** xplat `RequestProcessingService.java:1497–1518` and Paper `PaperRequestProcessingService.java:1921–1958` drain a ticket by UUID and consult the current player state. Same-UUID/same-dimension replacement passes today's dimension check and can start old work through the replacement player. Compare the request's captured registration identity against the current state before `submitGeneration`, current-player world access or rejection feedback. A stale ticket is retired without generating a fresh-session failure. Regression: hold the common ticket queue before platform admission, replace the registration, then drain; assert no platform submission and no fresh pending/counter mutation. The buffered-ready regression alone does not cover this boundary.

2. **Carry ownership on deferred removal as well as results.** `OffThreadProcessor.applyEvents`, lines800–807, consumes UUID-only removals; `removeGenerationTracking(UUID)` and `DedupTracker.removePlayer(UUID)` can sweep any registration represented by that UUID. Capture the retired registration in the lossless removal event and scope cleanup to that identity. Capture recipient identity before the player state is published, and make repeat registration reuse that same identity. Do not independently manufacture one token in the reader and another in player state. Add a queued-old-removal/fresh-admission control in addition to old-completion controls.

3. **Preserve the world miss-memo invalidation separately from registration-owned mutation.** `processGenerationReady`1538–1553 deliberately calls `timestampCache.clearMiss` for every generation outcome, including player-gone/dimension-change outcomes, before consuming per-player tracking. The dedicated regression family in `OffThreadProcessorDiskResultTest.java:1682` pins this because a completed generation can change world truth for another player. Rejecting an obsolete owner must precede pending removal, taint consumption, delivery, deposit and done-bit mutation; it should not accidentally suppress the safe world-scoped miss invalidation. Keep its existing control green with explicit identities.

4. **Clarify WI-2c's “must not cancel valid attached recipients.”** The existing accepted behavior is cancellation of the departing primary's group, silent release of followers' pending slots, then successful re-declaration: `DedupFanoutTest.primaryDisconnectFreesAttachmentsSilentlyAndTheirReRequestIsServed` at444 and `cleanupDedupGroups`934–951. Retaining followers behind an unreadable detached primary queue would wedge them. The plan already permits resubmission; explicitly retain the existing release/re-declare behavior unless a separate shared-result sink is actually introduced. Either approach must preserve follower convergence, accounting, dirty taint and each follower's registration identity. Do not turn this repair into mandatory shared-load transfer merely to satisfy an ambiguous sentence.

## WI-6 — implementation clarification

The new OFF withdrawal should bypass ordinary broadcast cadence and the client-triggerable full-roster rate bound, but only for server mode transitions. Existing `FarPlayerBroadcastService.tickViewer` uses `FULL_ROSTER_MIN_INTERVAL_MILLIS`; `FarPlayerBroadcastServiceTest.anyPrefsReceiptQueuesAFullRosterButTheRateBoundHoldsIt`102 pins that protection. Keep an explicit control-transition/pending-clear state distinct from ordinary `fullRosterPending`, or otherwise make the bypass's ownership unambiguous. Test OFF immediately after a successful full roster without advancing the clock beyond the normal full-roster interval, alongside the unchanged preference-rate-limit test. The plan's transactional clear acceptance, retry while OFF and rapid OFF→ON supersession rules are otherwise sound. Do not implement withdrawal by running the ordinary target snapshot builder with an empty online list: today's tick requires a viewer snapshot and skips all viewers if that list is empty.
