# Known test flakes and environmental failures

## The rule

A red is explained, not retried. No retry, longer deadline or looser assertion goes in without a
named mechanism and a test that is red without the fix. 22 of the first 36 entries below ended in a
code fix, three of them in the mod itself, and a loosened assertion once hid a test that tested
nothing for three months.

CI retries a failed step once only when every failure of the first attempt matches an open entry in
`config/test-flakes.json` (`tools/verify/flake_gate.py`). An entry names a cause that cannot be
fixed in this repository yet and carries an expiry date; past it, the entry allows nothing until the
cause is fixed or the entry is renewed with a reason. The first attempt's logs are always kept.
Everything below is the record of what each signature turned out to be.

## Entries

- **`XaeroBandFillTest.aCancelledJobLandsNoTile` (Fabric, Tier 1): a test baseline race, FIXED 2026-11-13. Not a flake: one red on the 1.21.1 line's CI (PR #394, second run).**
  - **Signature.** `no fill offer: XaeroMap: state=active, queued=2, … band_fill_last=5 0/4 running` after 10 s (`awaitOffered`).

When the worker had already offered before that read, the target was out of reach: these tests set the queue mark equal to the number they wait for, so the worker stops at the mark and never offers the extra tiles.

  - **Fix.** `switchTo` records the baseline before it switches, and `awaitOffered` counts from it.
  - **Rate.** A 300 ms diagnostic pause before the baseline read made all four fail on the first run with this message; with the fix the same paused run passed 32 of 32. The pause is not in the tree.
  - **Action.** A red with this signature now means the worker really stopped offering. Do not re-run it away.
  - **Evidence.** `~/.local/state/lss-program-2026-11/evidence/pr394-second-attempt/`.

- **`OffThreadProcessorDiskResultTest.notFoundInvalidatesAStaleTimestampStamp` (common, Tier 1): a test phase-order race, FIXED 2026-11-13. Not a flake: one red on the 1.21.1 line's CI (PR #394, a change that touched no Java).**
  - **Signature.** `timed out waiting for: re-read submitted` after the full 30 s (`waitFor`, `OffThreadProcessorDiskResultTest.java:240`).
  - **Mechanism.** A processing cycle runs: phase-1 events, disk results (the column is enqueued here), generation outcomes, the late drain of dirty events, then routing. The test waited for the enqueued column, then from its own thread queued the done-bit clear and enqueued the reopening request. When both landed between that same cycle's late drain and its routing, the request routed against the still-set done-bit, no disk read was submitted, and nothing asked again, so the wait could never finish.
  - **Reach.** Tests only. In production the dirty broadcast makes the client ask again after the clear. The same shape was in `unservableInvalidatesAStaleTimestampStamp` (added in 0.21.0) and is fixed with it.
  - **Fix.** Both tests issue the clear and the request through `beforeRouteAction`, which runs on the processing thread ahead of a cycle's late drain, so the clear is always applied before the request routes, whichever cycle picks the action up.
  - **Rate.** A 150 ms diagnostic pause between the late drain and routing reproduced the exact timeout on the first run; with the fix the same paused control passed (0.65 s). The pause is not in the tree.
  - **Action.** A red with this signature now means the done-bit clear or the late drain regressed. Do not re-run it away.
  - **Evidence.** `~/.local/state/lss-program-2026-11/evidence/pr394-first-attempt/` (the CI test report).

- **`OffThreadProcessorStoreTest.authoritativeNotFoundDeletesTheStoreRowButErrorTriageDoesNot` (common, Tier 1): a race in the test rig's `admit`, FIXED 2026-11-13 (0.23.0 branch). Not a flake: one red in a local run of the common, Fabric and Paper suites together.**
  - **Signature.** `timed out awaiting error-triage drain` after the rig's 3 s (`Rig.await`, `OffThreadProcessorStoreTest.java:129`, reached from the test's second `admit`). The test takes 20 ms when it passes.
  - **Mechanism.** `admit` offered a request, read the routing-cycle counter, and waited for it to grow by one. The rig's `await` keeps posting cycles, so after the test's first half a cycle can be in flight. When that cycle had already drained the requests and had not yet bumped the counter, it finished without routing the new request and `admit` returned. The test then queued the read result; the next cycle handles results before it routes, found no pending request for the result and dropped it, then routed the request, whose stubbed read never answers.   - **Rate.** A 150 ms diagnostic pause before the counter bump reproduced the exact timeout on the first run; with the fix the same paused control passed. The pause is not in the tree.

- **`XaeroLoadPixelParityTest` (16 tests) and `JourneyMapDecoderParityTest` (3 tests), `AssertionError` in Mockito's `MockUtil.getMockHandlerOrNull` (Fabric, Tier 1): a second mock maker in the test JVM, FIXED 2026-11-12 (0.21.0 train). Not a flake: 19 reds in one 26.1 full gate, green on the re-run.**
  - **Signature.** `java.lang.AssertionError` with no message at `org.mockito.internal.util.MockUtil.getMockHandlerOrNull(MockUtil.java:160)`, reached from the first `thenReturn` on a mocked `Level` (`XaeroLoadPixelParityTest.assertParity`, `JourneyMapDecoderParityTest.decode`). Every test that stubs a `Level` fails and nothing else does.
  - **Mechanism.** `DhClientSessionTest` built its Minecraft doubles with `withSettings().mockMaker(MockMakers.SUBCLASS)`. Naming a maker registers it for the whole JVM, beside the default inline maker. To find a mock's handler, Mockito 5.20.0 asks each registered maker in the iteration order of a hash map keyed by the maker's `Class`, and asserts that the first maker to recognise the mock is the one that made it. The subclass maker recognises every generated subclass (`mock instanceof MockAccess`), and a generated subclass is what the inline maker builds for an abstract type or an interface. `Level` is abstract. Once the subclass maker was registered, a stubbing on `mock(Level.class)` threw when that maker was walked first and passed when it was not: the identity hashes of two `Class` objects decide. A mock of a concrete class is an instance of that class, which the subclass maker does not recognise, so `VoxyVanillaCoverageTest` and `ChunkDiskReaderTest` stayed green in the same JVM.
  - **Why a gate saw it.** Gradle runs the classes in name order, so `DhClientSessionTest` normally runs after both parity tests and registers the second maker too late to matter. Gradle also runs the classes that failed in the previous run first, and after an earlier red run of the same tree that put `DhClientSessionTest` ahead of them. A new test that sorts after `networking.client` and mocks an abstract type or an interface would have failed the same way in name order.
  - **Reach.** Tests only. The Fabric test JVM on all six lines (the same lines of `DhClientSessionTest`), including `test-fixtures/dh-live` `ContentProbeTest` when `fixture-tests.gradle` adds it to that JVM. Paper pins the same Mockito and names no maker. NeoForge, Sponge and common do not use Mockito.
  - **Fix.** Both tests make every double with the default maker, so the JVM has one maker. Nothing recorded why the subclass maker was chosen. For these doubles it differs in final methods, which it runs for real on an object no constructor initialised and the inline maker stubs. On every line the only Minecraft classes with final methods among the mocked ones and their superclasses are `Level` (`isDebug`), `MinecraftServer` (`overworld`), `Entity` and `LivingEntity`. `DhClientSessionTest` passes 126 of 126 with the default maker: first in the JVM, alone and in the full suite. `SingleMockMakerContractTest` reds on a test source that names a maker. Mockito fixed the lookup in 5.24.0 (mockito/mockito#3795, issues #3406 and #2823). The pin stays at 5.20.0, four feature releases behind it; once the pin reaches 5.24.0 the contract test can go.
  - **Rate.** `DhClientSessionTest` forced first, one fresh test JVM per run, a different count of identity hashes consumed before each: 2 of 7 red before the fix, both with exactly these 19 failures and the subclass maker walked first; 0 of 7 after, with the same seven seeds. The same three calls outside Gradle: 7 of 24 seeds red on Mockito 5.20.0, 0 of 24 on 5.24.0. The full 26.3 `:fabric:test` is green in name order and with `DhClientSessionTest` forced first.
  - **Action.** A red with this signature means a second mock maker is back in a test JVM. Find it (`MockMakers`, `mockMaker`). Do not re-run it away.
  - **Evidence.** `~/.local/state/lss-release-prep-v0.21.0/port-26.1/full2-first-attempt/` (the gate red) and `~/.local/state/lss-release-prep-v0.21.0/mockito-evidence/` (its `README.txt` maps the reproduction device, the runs before and after, the standalone reproduction and the Mockito sources).

- **`BacklogReplaceTest.concurrentHoldReleaseNeverRestsAStaleBatchAndBalancesAccounting` (common, Tier 1): a guard-pairing defect in the Folia hold-release, FIXED 2026-11-12 (0.21.0 train). Not a flake: one red in a 26.3 full gate, green on the re-run.**
  - **Signature.** `round 3589: a STALE batch (id 7178 < newest consumed 7179) RESTED in the mailbox at quiescence — the retract guard failed (AbstractPlayerRequestState.republishHeldBatch)`. The `BrokenBarrierException` lines from `r8-pump`, `r8-offer` and `r8-take` are the harness stopping its workers after the failure.
  - **Mechanism.** `offerIncomingBatch` bumps the offer generation before it writes the mailbox. The pump labelled a hold with a counter read beside its take. Inside a newer offer's bump-to-write window that read returns the newer generation while the take removes the older batch. Once the newer batch had been written and consumed, the counter still equalled the label and the mailbox was empty, so both `republishHeldBatch` guards passed and the stale batch rested.
  - **Reach.** Folia only. On 0.7.3 to 0.14.x the router consumed any pending batch, so a server could route one stale want-set until the client's next declaration (after an empty backpressure clear, it resumed serving a client that had asked it to stop). Since 0.15.0 the router consumes only batches the pump released, so nothing can pass through the mailbox during a hold and production could not reach the window. The test's plain `takeIncomingBatch()` consumer could.
  - **Fix.** `takeFreshIncomingBatchForProbe` returns the batch together with its own offer generation, read from the envelope the take removed, and the Paper pump releases under that. `BacklogReplaceTest.aHoldTakenInsideANewerOffersBumpToWriteWindowIsNeverRepublished` and `RegionProbeSchedulingTest.aHoldTakenInsideANewerOffersBumpToWriteWindowDiesAtTheRelease` put the hold inside the window through the `beforeOfferWrite` seam. Both are red on the old pairing.
  - **Rate.** Old pairing: 0 of 160 isolated runs of the unamplified harness (the window is tens of nanoseconds), 40 of 40 with the window and the hold widened to microseconds. Own pairing: 0 of 80 and 0 of 40 under the same two harnesses.
  - **Action.** A red with this signature is a regression in the guard ladder. Do not re-run it away.
  - **Evidence.** `~/.local/state/lss-release-prep-v0.21.0/server-evidence/full1-first-attempt/` (the gate red) and `~/.local/state/lss-release-prep-v0.21.0/race-evidence/` (reproduction, mutation reds, final runs).

- **`ServiceLifecycleGameTests.regionFreshnessServesRealRegionHeaders` (Tier 2): a real summary-pipeline liveness defect, FIXED 2026-10-14 (0.19.0 fold); the `SerializerParityGameTests` readiness red beside it was a test-side wall deadline, fixed the same day. Not flakes: two local reds on 26.1 (2026-10-12 0.18.0 restage; 2026-10-14 0.19.0 restage).**
  - **Signatures.** Region freshness: `one summary frame must assemble and send, reqs=1 frames=0 on tick 1202`, both sightings. Region freshness was in batch 1, which started at that same second, and failed at 04:13:00. "Tick 1202" is just each test's own `maxTicks` boundary.

The `Summary:` diag line gains `expired=`/`reassembled=` only when nonzero, and the gametest's failure message now carries that whole line plus the header-hit count. Its teardown also runs on a timeout now.
  - **Serializer parity.** Its native-readiness budget was a 10 s wall deadline set at the save and checked before the read was issued, so a stall between two ticks spent it ("not yet read"). The budget now starts at the first readiness tick and is checked after that tick's poll.
  - **Disk-read timeouts.** The three `Disk read timed out (>10s)` lines at 04:08:58 are in the Fabric gametest server's own log (`26.1-attempt1/gametest-logs/latest.log`, the same JVM as both failures), not the NeoForge one. They fell in batch 0 and did not involve the summary path.
