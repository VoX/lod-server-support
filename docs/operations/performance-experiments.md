# Fixed reference-machine experiments

Functional diagnostics do not establish performance acceptance. Finish the independent source/receipt oracle, actual four-client readiness, deferred-consumer and admission controls, debt drain and owned-process cleanup first. Performance runs require an idle host, the same frozen world/store/cache snapshot and fixture bytes, and the exact preregistered baseline artifacts. The original experiment uses pre-improvement artifacts. A separately registered correctness-corrected reference must retain its exact original-plus-correction attribution, preserve the failed original experiment, and explicitly exclude the correction cost from the claimed improvement comparison. Both arms must contain the same shared correctness fixes. This comparison measures the remaining improvements, not the total cost of the original-to-final changes. Merely disabling the new status collector in candidate code is not a baseline.

`tools/rig/metric-schema.json` defines the protocol. `assemble_metrics.py` retains every subject's raw duration and RSS errors. Useful bytes require an actual body receipt identity and an independently validated target outcome. One body satisfying several targets counts once. Aggregate frame statistics pool real frames while preserving each client's statistics; useful throughput sums eligible-subject rates; aggregate RSS is the simultaneous total, not the sum of peaks observed at different times. Missing samples stay missing.

`tools/rig/experiment.py` records three calibration slots and exactly six measured slots in baseline/candidate, candidate/baseline, baseline/candidate order. Create a new directory with `init --input REGISTRATION.json`. The registration names both source/artifact identities and the world, dependency profile, fixture, hardware, JVM and workload digests. Before creating each runtime, obtain `intent --phase calibration` (later `--phase measured`) and include the returned object as `runtime.measurement_context`, so the runtime hash binds the slot before launch. `record --input REPORT.json` consumes that slot once, including failed results. Failed selected runs cannot be replaced within the experiment. If collection fails or report assembly cannot produce a valid report, use `record-failure EXPERIMENT_DIR --input COLLECTED_RUN_DIR`. This verifies the original selected intent, manifest and completed owned-process cleanup, then consumes the slot with failure evidence and no metric values. That explicit failure is terminal: no replacement, later intent or successful evaluation is allowed. Missing or changed staged bytes can themselves explain failure; recording their intended manifest identity does not certify those bytes as unchanged.

After three separate baseline calibration runs, `freeze` checks correctness, sample sufficiency and baseline stability before recording numeric floors. Only then can measured intents be created. `evaluate` rechecks the original calibration evidence, derived floors, exact measured intents and alternating order before invoking the performance checker. Editing floors or relabeling candidate artifacts as baseline invalidates the experiment. A separate investigation does not replace a selected failed pair.

The raw-run report adapter and live measurement workflow must verify these identities against the owned run; hand-authored summary values or boolean declarations are not evidence. The implementation ledger records whether actual calibration and measured runs have completed. No numeric conservative preset is justified until the accepted measurements exist.


The maintained measured producer is a separate mode (`-Dlss.rig.measuredWorkload=true`). It seeds 256 distinct loaded columns per subject at local chunk X 12–27 and Z -7–8, separated from the four original source-provenance corners. The source-seed checker requires all 1,024 additional cells to be retained and present on disk before permitting a measured snapshot. A diagnostic snapshot with only sixteen corners cannot satisfy this premise.

`MeasuredSchedule` offers one four-subject round every 125 ms for 720 seconds: 5,760 targets per subject and 23,040 total, with a 32-second revisit period per cell. Each edit changes its cell between gold and diamond. The producer publishes targets before owner-thread edits, waits for the client's oracle acknowledgement, and bounds pending edits. It emits at most one round per owner tick and fails if it falls more than one second behind or misses any scheduled round. `check_measured_schedule.py` independently verifies every sequence, position, expected block, deadline and close marker before report assembly. Completed subjects or missing requests cannot reduce the preregistered offered load.

The Java schedule control under `test-fixtures/concurrent-server-core/test/` checks the complete 20 Hz owner-tick schedule, target-domain uniqueness and radius, revisit spacing, and delayed/truncated-producer rejection. Python seed and offered-load controls reject missing/duplicate cells and targets, unbound measured mode, changed positions and burst timing. These are fixture controls; the implementation ledger separately records actual measured execution.
